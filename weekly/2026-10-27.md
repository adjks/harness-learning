# Weekly Harness Notes - 2026-10-27

## 本周结论

本周的新增证据把关注点从“让单个 agent 更聪明”转向**把 agent 产生的工作量当作受控流量**：Harness 的一线数据表明，代码、PR、拉取和 CI 会比人员数量快得多地增长；Infobip 的实践把人类判断前置到研究和任务定义；两篇实证研究分别提醒，不能把所有上下文压缩或所有子 agent 泛化为同一种优化。新上榜的 `ai-memory` 与 `headroom` 则展示了两条不同的状态管理路径：跨工具的、可恢复的事实/交接记录，以及可按需取回原文的可逆压缩。

## 本周新增资料

### 1. Harness：agent 规模化后，SCM 与 CI 的并发、读取和验证吞吐成为主约束

来源：[When Code Stops Being the Bottleneck: Scaling Source Control and CI for AI Agents](https://www.harness.io/blog/when-code-stops-being-the-bottleneck)（2026-10-22，10-23 更新）。这是新的团队 dogfooding 报告，未在此前周报覆盖。

- **有价值的点**：它给出了“agent 改变了什么”的运行数据，而非只谈模型：其工程组织的 PR 约增至 7 倍、push 6.6 倍、仓库读取近 6 倍、CI 执行近 7 倍，但活跃贡献者只约增 30%。读操作比写操作增长快，说明 clone、测试和 agent 查阅仓库是新的主负载。
- **痛点**：agent 的“改一点—推送—等检查—读失败—再推送”循环会把一个任务放大成多次 clone、PR check 和 CI；峰值时即便计算资源尚有余量，也会因并发配额而排队，反馈回路变慢。
- **方法 / 机制**：报告采取 server-side repository/PR read API 与 MCP，避免每个 agent 都 clone；用以 commit 与 client flags 为键的短时 clone cache，优化只读 merge verification，加入 merge queue，并对 CI 使用跨地域分流、warm pool、fallback 与基于历史的预测扩容。运行中还会暂时停用高量、非关键 trigger 来清 backlog。
- **效果 / 结果**：作者报告 clone latency 降 40%、其 merge-verification 工作量在多副本下约降三分之二，并称更新后的平台能在不拖慢构建系统的情况下服务 7 倍负载、已压测 10 倍流量。这些是供应商自报，**待验证**于其他组织；但“先测验证通道的队列与读取成本，再增加 agent 并发”是可直接迁移的结论。

### 2. Infobip：把人类审查压在错误传播最昂贵的上游，而不是在生成代码后无止境返工

来源：[A Phased Workflow for Operating LLM-Based Coding Agents](https://arxiv.org/abs/2608.30701)（2026-08-31）及其公开的 [agentic-development-workflow](https://github.com/infobip/agentic-development-workflow)。这是新的、来自工程团队的工作流报告；虽非本周发表，但此前资料库未收录，且本周与吞吐/上下文问题形成直接互证。

- **有价值的点**：团队将 agent 开发分为 research、planning、task definition、implementation 四阶段。research/planning 对一个项目做一次，后两阶段按任务重复；越靠前，人类参与越多，避免未经验证的研究结论层层传进计划和代码。
- **痛点**：把长对话直接延续到实现，既会累积无关信息、错误假设和互相冲突的决定，也会让“修补生成物”替代了纠正错误任务定义，最终得到臃肿、脆弱的实现。
- **方法 / 机制**：research 阶段只给只读搜索和领域工具，先验证发现；planning 结束后由人把已验证决策手工收敛成持久 artifact，替代整段聊天记录；每阶段显式选择 write（外存）、select（检索）、compress（只留必要内容）、isolate（分会话/agent）。若实现揭示任务定义不良，应回到 task definition，不在实现循环中硬补。
- **效果 / 结果**：论文将这描述为团队经验和可复用流程，未给出对照实验的完成率或成本，因此不能据此宣称必然更快。其有力之处是把“何时由谁批准哪一种 artifact”变成流程接口；个人可先为每个改动保留 `research → decisions → task → evidence` 四个小文件，而非堆叠聊天记录。

### 3. 实证研究：结构化工具与任务专属委派较稳；激进压缩和通用子 agent 可能反而伤害结果

来源：[Beyond the Model: Demystifying Harness Effects in Software Engineering Agents](https://arxiv.org/abs/2609.32459)（2026-09-26）。此前仅收录了治理/成本方向的论文；这是新的组件级实证补充。

- **有价值的点**：研究者将 NanoHarness 拆成 tool registry、planning、lazy skills、context、task-specific/general subagents 等组件，在 ProgramBench 上对 Qwen3.7-Max 与 DeepSeek-V4-Pro 做消融。两种模型中，tool registry 与 task-specific subagents 的单项改善最稳定；全组合相对 mini-SWE-agent 分别提高 7.37 和 6.21 个百分点。
- **痛点**：实践里常把“压缩上下文”“多开子 agent”“加 plan”当作普适增益，导致为了节省 token 或显得更自动化而抹掉需求、调试状态，或引入无关的协调开销。
- **方法 / 机制**：组件必须按任务形态组合：专属子 agent 接到明确的仓库操作/验收目标，通用子 agent 不等同于“再增加一个思考者”；压缩若使用，应保留可检索的原始需求、接口约束与失败状态，而非只留摘要。实验中压缩将 prompt token 降约 54%/77%，却带来 4.86/3.85 个百分点得分下降。
- **效果 / 结果**：这是受控 benchmark 证据，不是生产 SLA；它不能证明某一实现会在所有真实仓库胜出。可行动的**推断**是：把压缩和委派都设为可实验的 feature flag，记录 token、工具调用、验证通过率与回滚/返工，而不要作为全局默认。

### 4. 趋势仓库 `akitaonrails/ai-memory`：交接记录应是有所有者、可认领、可恢复且能老化的共享事实

来源：[akitaonrails/ai-memory](https://github.com/akitaonrails/ai-memory)（本周 general weekly 与 AI-agents 主题视图发现并检查 README）。这是新仓库，不是此前记录的 `claude-mem` 或 `MemoHarness` 的重复。

- **有价值的点**：它将跨 Claude Code、Codex、Cursor 等工具的 handoff 做成 typed protocol：交接有 owner 且只能 claim 一次；项目知识和个人 handoff 分开。存储源是 git-backed Markdown wiki，数据库只是可重建索引。
- **痛点**：单一 agent 的 memory 往往只在一台机器或一个客户端生效；切换模型、工具或同事后，失败过的方案、未决问题和实际决策被迫重新解释。无限累积的记忆又会腐化为噪声。
- **方法 / 机制**：`ai-memory run` 为下一个 agent 提供共享 workstream 和临时本地 history projection；服务端仅接收 harness/session identity，而不接收本地 transcript 路径或正文。lifecycle hook 在 typed privacy boundary 清洗数据；记忆按 tier 做可调度衰减、按使用减缓衰减、合并近重复并标记潜在冲突，原始内容通过 Git 保留且可恢复。
- **效果 / 结果**：README 可验证的是协议、隐私边界和可运行实现，不是“跨 agent 一定不会遗漏”的独立指标。采用时需先验证实际 hook 会采集哪些 prompt/tool 内容、团队服务器 ACL 与保留策略；最小可行实践是只同步决策、失败路径、未决项、验证命令和 artifact 链接。

### 5. 趋势仓库 `headroomlabs-ai/headroom`：把压缩改造成局部、可逆、可度量的读取优化

来源：[headroomlabs-ai/headroom](https://github.com/headroomlabs-ai/headroom)（本周 MCP 主题视图发现并检查 README）。这是新仓库；它补充前周“上下文需新鲜”的主题，但采用不同的可逆技术路线。

- **有价值的点**：它压缩 tool output、日志、文件、RAG chunk 与 history，同时本地保存原文，并让模型通过 `headroom_retrieve` 按需取回。它提供 library、零代码 proxy、agent wrapper 与 MCP server，能把优化放在 agent 与 provider 之间而不改业务代码。
- **痛点**：测试日志和 JSON output 容易主导上下文及成本；但前述实证表明，直接把历史浓缩成摘要可能丢失之后调试需要的约束，单纯“减少 token”不是可靠性目标。
- **方法 / 机制**：ContentRouter 按 JSON / code AST / prose 选择压缩器；CacheAligner 仅标记可能破坏 provider KV-cache 前缀的易变内容，不重写 prompt；CCR 在本地缓存原文供检索。README 提供 `doctor`、`perf` 与 dashboard 来检查路由和节省是否真的生效。
- **效果 / 结果**：项目声称 coding agents 少用 20% token、JSON 少 60–95% token 且答案相同，但这是项目声明，尚非独立评测。与第 3 条合看，应该把其视为“对巨大、低语义密度输出的按需访问层”，并以测试 verdict、retrieval 次数和任务成功率确认没有过度压缩。

## 跨来源实践模式

1. **把 agent 视为流量生产者，而不是孤立的生产力工具**：并行 agent 数、重试频率、clone/read、CI queue、review backlog 与验证延迟应一起成为容量指标；不能只看 token 或 PR 数。
2. **上游 artifact 的人工验收能减少下游回合**：research findings、计划决策和 task acceptance criteria 都是可审查的控制点。实现失败时回滚到错误所属的阶段，不要用更多 agent 回合掩盖任务定义问题。
3. **上下文优化必须可逆、可观测、分类型**：高体积日志适合压缩并提供原文 retrieval；需求、接口和未决约束更应保存为可检索事实。压缩率不是成功指标，验证 verdict 才是。
4. **协作 memory 要区分公共项目知识、个人偏好与一次性交接**：每一类都需要 owner、scope、更新时间/衰减和恢复路径；共享并不代表无边界地上传所有 transcript。

## 对个人 AI 工作流的建议

- 在启动多个 agent 前先为验证资源设预算：最大并行 PR/check 数、每任务最多 retry、何时合并小改动；若 CI queue 或 review backlog 超阈值，先暂停新派发而不是继续扩容。
- 用一个短的“handoff packet”替代长会话续聊：目标、已验证事实、已否定方案、文件/命令、未决问题、下一步 owner；把可恢复原文放在本地或受控存储。
- 对 compression、skills 和 subagents 逐项做 A/B：记录输入 token、retrieval、耗时、独立测试/静态检查 verdict 和返工；若压缩后失败率上升，优先恢复关键 artifact，而非继续压缩。

## 对项目的影响与待验证项

- **项目影响**：若本仓库后续实现 harness 原型，应先补一个 run-level capacity ledger（agent、任务、读取/clone、CI、verdict、队列等待），再扩展复杂 multi-agent 调度；这将把本周的团队容量证据变为可观察的本地实验。
- **待验证**：Harness 的 7 倍增长和延迟改善来自自身平台与组织，是否迁移到小团队/公共 GitHub Actions 仍未知；应采集本项目的基线后再定阈值。
- **推断**：`ai-memory` 的 ownership/claim 与 `headroom` 的可逆 retrieval 组合，或可同时降低交接遗漏和 context 成本；但二者的 hook、权限、数据保留和性能开销须在隔离测试目录中先审计，不能直接对真实私有仓库默认开启。
