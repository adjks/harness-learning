# Weekly Harness Notes - 2026-10-11

## 本周结论

本周的增量信号是：当 agent 的触及面从仓库扩大到并行流程、桌面 GUI 和本地工具时，**编排、隔离与验证要由不同的、可审计的层负责**。把顺序、并发、暂停和双重确认写成 workflow code；把文件、网络和凭据约束交给 OS 级 policy；把安全检测和测试保留为独立 oracle。个人效率的另一面则是避免把原始工具输出塞回聊天记录：将大输入留在受控存储中，只按当前任务检索所需证据，并在恢复任务时重新验证它是否仍然适用。

写作前已扫描所有既有 `weekly/*.md`、`sources.md` 和自动化记忆，并排除已详细记录的 Copilot 本地 sandbox preview、OTel、Copilot Memory、Claude dynamic workflows、Codex harness/Agents API 等资料。检查了 GitHub Trending general daily/weekly、Python weekly、TypeScript weekly 与 Jupyter Notebook weekly，以及 AI agents/developer tools/MCP/testing/verification 相关候选；不按 star 数入选。以下均为本周首次详细收录，或明确说明已有资料的本周新增点。

### 1. GitHub Copilot Dynamic Workflows：将可复用控制流与模型判断分离

来源：[Dynamic workflows in Copilot CLI and the Copilot app](https://github.blog/changelog/2026-10-01-dynamic-workflows-in-copilot-cli-and-the-copilot-app/)（2026-10-01）。

- **有价值的点**：Copilot 将 multi-agent 的可靠性与可观测性落在 extension 中的可执行程序，而不是一条巨型 prompt。程序定义步骤、串并行、何时调用 agent、怎样消费结构化结果；agent 只承担需要判断或分析的局部工作。
- **痛点**：同类发布检查、PR 批量 review 或 incident 调查若全靠临场对话，阶段、预算、暂停点和结论合并方式不可复现；单一 agent 也不应既提出结论又成为唯一裁决者。
- **方法/机制**：官方给出的模式包括：release checks → agent 分析失败 → 人工 review 后再恢复；按目录并行审查大 PR；用代码找已合并 PR 的未解决评论，再让两个模型独立判断且仅在二者一致时报告。它适合存在清晰阶段、检查或上限的任务；简单改动仍应使用普通会话。CLI 目前须开启 experimental，能力处于 public preview。
- **效果/结果**：公告没有发布通过率、误报率或成本对照，效果**待验证**。可直接借用的最小结构是 `collect -> deterministic_check -> independent_review -> human_gate -> apply`，每一阶段写出 input hash、输出 schema、超时和 `on_failure`；不要把“两个 agent 同意”误作充分的正确性证明。

### 2. Copilot local sandbox 从 preview 到 GA：隔离成为可依赖的 tool-policy 层

来源：[Local sandboxing for GitHub Copilot now generally available](https://github.blog/changelog/2026-10-07-local-sandboxing-for-github-copilot-now-generally-available/)（2026-10-07）；本库已收录 2026-09-23 的 preview，**本周新增信息是 GA 覆盖 Copilot CLI、Copilot app 与使用 Agent Host 的 VS Code session，并明确以 MXC 将统一 policy 翻译为 Windows/macOS/Linux 原生控制。**

- **有价值的点**：官方明确区分 model execution 与 tool isolation。无论请求由哪个模型处理，文件、网络、凭据和本地服务的实际访问权由 sandbox policy 裁决，企业可强制且开发者不能放宽。
- **痛点**：仅靠 prompt 要求 agent “不要读/写/联网”无法形成硬边界；换模型或换 UI 后若需重写安全假设，会让治理成为脆弱的模型配置。
- **方法/机制**：policy 可限制命令能读写的路径、互联网/局域网、Git 与 GitHub CLI 凭据，并在支持处覆盖 local MCP、语言服务等本地工具。MXC 负责将共同 policy 映射到不同 OS 的实际隔离能力。
- **效果/结果**：GA 表示支持面与稳定性承诺提高，但公告没有提供越权阻断率、兼容性或性能数据，仍属**待验证**。项目侧应把 `policy manifest` 和每次 run 的 effective policy 一同存档；测试“拒绝写入/拒绝联网”是否真的失败，而不是只测试允许路径。

### 3. GitHub 的专用 secrets classifier：把 agent security review 接到一个前置、可计费且可关闭的 gate

来源：[Purpose-built model for leaked secret detection](https://github.blog/changelog/2026-10-07-purpose-built-model-for-leaked-secret-detection/)（2026-10-07）。

- **有价值的点**：GitHub 将“疑似凭据”检测拆成专用的上下文分类器，而不是让生成式 agent 输出自然语言判断；该模型阅读周边代码识别无固定 token 格式的 password/credential。现有 alert 自动升级，push-time protection 与 Copilot `/security-review` 的额外检查则是显式 opt-in。
- **痛点**：生成式 review 对凭据泄露的结论可能不可预测，且让 agent 自动启用付费检查、改变 policy 或预算，会把安全和成本决策混进普通修复回合。
- **方法/机制**：在 commit/push/PR 前运行只读 `/security-review`，先返回排序后的发现和 remediation，再由获授权的人/agent 修改并重跑。新的 classifier 检查分别受组织 policy、资格和 AI Credits 预算控制；GitHub 特别说明 budget alert 本身不必然停止用量，需配置 stop-usage。push protection 目前仍为 private preview，review 的新检查也将是 opt-in preview。
- **效果/结果**：公告未给 precision、recall 或漏检数据，不能将“专用模型”视为已验证的安全保证，**待验证**。可迁移做法是将敏感内容检测放入提交前的独立、read-only gate，输出只含 finding id、证据位置和状态；将启用新检查/增加预算列为人工授权动作，并记录每次 gate 的版本和退出码。

### 4. OpenAI 团队的 Codex 使用手册：用后台队列保存碎片工作，再以可审查产物接回主线

来源：[How OpenAI uses Codex](https://cdn.openai.com/pdf/6a2631dc-783e-479b-b1a4-af0cfbd38630/how-openai-uses-codex.pdf)（本周发现的官方团队实践手册）。

- **有价值的点**：它提供了比“让 agent 自主完成任务”更具体的个人生产力边界：将 drive-by fix、探索、低覆盖模块补测等碎片任务发入 task queue；人保持当前分支和高优先级工作，稍后以 PR、计划或测试结果为交付物接回。
- **痛点**：on-call、会议和分支切换会打断深度工作；如果中断时只留下聊天历史，恢复者不知道待办、已验证事实和下一步，反而增加切换成本。
- **方法/机制**：大改动先用 Ask Mode 生成实施计划，再带入 Code Mode；把仓库惯例持久化到 `AGENTS.md`；以“定位低覆盖模块 → 生成可运行测试 PR → CI”或“扫描旧模式 → 输出 Markdown 影响面 → 建 PR”拆成可回收的后台任务。官方也建议给 prompt 加入具体模块、现有模式和验收约束，而非抽象地要求“优化”。
- **效果/结果**：手册中的节省时间和合并 PR 例子是团队轶事，未提供受控对照，**待验证**。个人可测量的假设是：将突发想法转换成带 `scope`、`acceptance_command`、`resume_note`、`expiry/commit` 的队列项，能降低恢复时间；应记录从创建到人工接回的时长、CI 首过率和过期任务率。

### 5. GitHub Trending `mksglu/context-mode`：让 agent 用代码处理大数据，并将 session state 变成按需检索的本地索引

来源：[mksglu/context-mode](https://github.com/mksglu/context-mode)（本周 GitHub Trending general daily、general weekly；README 于本周检查）。

- **有价值的点**：项目把上下文消耗拆成两个工程问题：大工具结果不直接回灌模型，而在 sandbox 中由脚本过滤/聚合；跨 compact 的文件编辑、git 操作、错误和用户决策存进 SQLite/FTS5，仅以 BM25 返回当前相关片段。它支持 Claude Code、Copilot CLI/VS Code、Cursor 等多种客户端的 hook/MCP 接入。
- **痛点**：浏览器 snapshot、日志或批量 issue 会迅速挤掉上下文；compact 后若无可检索状态，agent 容易重读文件、重复工具调用或误接续旧任务。
- **方法/机制**：README 所述的 `ctx_execute`/batch sandbox tool 倡导“model 写分析程序、程序只输出结果”，配合 `SessionStart`、`PreToolUse`、`PostToolUse`、`PreCompact`、`Stop` 等 hook 路由和记录。其默认语义是没有 `--continue` 时删除此前 session data；提供 doctor、stats、purge 等工具检查配置与清理索引。
- **效果/结果**：README 声称某些示例可从 315 KB 降至 5.4 KB（98%），并列出团队采用标志，但这些是项目自报，未见独立 benchmark，**待验证**。可迁移内核不是直接安装该项目，而是：先在本地/受控 store 处理原始数据，给模型返回带 provenance 的小摘要；恢复时按 task/commit 查询并对关键事实重验。隐私边界也要先审查：哪些事件、路径、命令摘要或检索索引可保留，及其 purge/retention 规则。

## 跨来源实践模式

1. **把控制流写成可审计资产。** 任务有复用价值、并发、暂停、审批或费用上限时，显式保存阶段图、输入输出 schema 与 stop reason；模型输出只是一个阶段产物。
2. **将能力范围、工作流权限与结论正确性分层。** sandbox 决定工具能否做；policy/budget 决定是否允许启用能力；测试、secret classifier、人工审批决定产物能否越过 gate。三者不能用同一句 prompt 替代。
3. **以队列而不是上下文硬撑来保护专注。** 让 agent 先把旁路工作产出为计划、PR、测试或可验证报告；恢复任务需要 `resume_note`，但事实应绑定提交和有效期。
4. **大输入先在工具侧计算，模型侧只消费证据。** 保留原始日志/页面的可定位引用和最小结果；任何索引与 memory 都应有 retention、purge 和当前代码 freshness 检查。
5. **自动化开关本身是高风险动作。** 新的付费检查、扩大本地权限、桌面/网络访问或新模型默认值，应作为变更请求记录 owner、policy 依据、预算和回滚，而不是由执行中的 agent 自行开启。

## 对个人 AI 工作流的建议

- 为每个长任务创建 `workflow.yaml` 或等价记录：`stages`、并发限制、`oracle_command`、`max_attempts`、`human_gate`、`timeout` 与 `stop_reason`；只将能被重复使用的流程固化，普通改动保持轻量。
- 在 pre-commit/PR 前增加独立的 secret/敏感文件 gate；默认只读、失败即阻止后续自动 push，并把“开启云扫描或增加额度”留给显式确认。
- 将所有后台 agent task 交付为一个可审查包：`scope`、base commit、diff/PR、验证命令及其原始退出状态、未决风险和下次恢复入口；过期或基线变更后自动降为需复验。
- 面对大日志、网页或仓库分析，优先让 agent 写小脚本产生结构化摘要，并同时记录查询/脚本版本与原始数据位置；不要无界地把 tool output 追加进对话。
- 为 memory 设定“检索不等于信任”：检索条目至少带 source、commit、生成时间、适用范围和 purge/expiry；触及写入、权限或安全结论时，必须重跑当前证据。

## 对项目的含义

当前 CodeGuard/个人 harness 更值得新增的是一个**workflow run envelope**，而不是新的 agent loop：它连接 `policy manifest`、阶段 DAG、输入/产物 hash、命令 exit code、独立 safety findings、human approval 与统一 stop reason。将 `context summary` 与原始 evidence 分离存储；summary 只作为检索入口，任何可改变代码、发布或权限的动作均回到原始证据和当前 commit 的 verifier。对于高开销或敏感扫描，可在 envelope 内增加 `capability_request` 状态（requested/approved/denied/expired）并固定预算/责任人。

## 推断与待验证

- **待验证**：Dynamic Workflows 的双模型一致性是否真的提高 review precision，还是只加倍成本并放大共同偏见；应以人工裁定样本比较 precision、召回、延迟和每项 confirmed 成本。
- **待验证**：Copilot local sandbox 的 GA 跨平台 policy 是否在 local MCP/语言服务器等边缘工具上保持一致；应使用 allow/deny 测试矩阵和实际 effective-policy 导出验证，而非只检查配置文件。
- **待验证**：专用 secret classifier 对无固定格式凭据的召回/误报表现；个人项目不应以 vendor 公告替代自身代码库上的 blind evaluation。
- **推断**：队列化旁路任务与可恢复 evidence package 能减少中断后的重新定位时间；应记录恢复耗时、任务过期率与人工拒绝原因验证。
- **推断**：工具侧计算与按需检索可以降低上下文浪费，但持久索引若缺乏 retention 与访问边界，会把效率问题转为隐私/陈旧信息风险。
