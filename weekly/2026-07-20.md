# Weekly Harness Notes - 2026-07-20

## 本周结论

本周最强的共同信号不是“再增加一个 agent”，而是把 agent 放进**可检索、可验证、可隔离**的任务环境：小而可导航的知识入口、任务级证据与评测、worktree 隔离，以及明确的人类审批点。多 agent/并行 worktree 已开始产品化，但只有在任务能独立拆分且验收能比较时才值得使用。

## 重要来源拆解

### 1. OpenAI：Harness engineering

来源：[Harness engineering: leveraging Codex in an agent-first world](https://openai.com/index/harness-engineering/)

**有价值的点。** 将 harness 落在工程环境而不是 prompt 技巧：UI、日志、指标、链路追踪和本地开发环境都成为 Codex 可操作、可观察的对象。文章报告了内部产品实验；这里应学习工作方式，而不是外推其产出数字。

**痛点。** 环境信息不足会让 agent 卡住；巨大的 `AGENTS.md` 又会挤占任务上下文并快速过时。吞吐提高后，纯人工 QA 成为瓶颈。

**方法 / 机制。** 短 `AGENTS.md` 只做目录，详细知识进入带索引的仓库文档；每个 worktree 启动独立应用和临时可观测栈；agent 用浏览器快照、LogQL、PromQL/TraceQL、测试和本地脚本自己重现、修改、复验。以 CI/linters 检查知识库链接与新鲜度，并用“doc gardening”清理陈旧规则。

**效果 / 结果。** 团队称该设计将 QA 从人工目测转为反馈循环，并在内部实验中得到高 PR 吞吐。对个人更可信的结果是：任务从“请修好它”变为“在隔离环境中满足这些可执行证据”，返工风险会更低。

### 2. OpenAI：用生产证据驱动自我改进 agent

来源：[Building self-improving tax agents with Codex](https://openai.com/index/building-self-improving-tax-agents-with-codex/)

**有价值的点。** 生产纠错不直接变成 prompt，而是先被人工审阅、归类成有清晰成功条件的失败样本，再进入修复循环；“用户反馈”因此成为可复现的工程输入。

**痛点。** 原始反馈可能是噪声、产品能力缺失、判分器错误或需要专业判断。自动化每条反馈会自动化错误目标。

**方法 / 机制。** 将 trace、源材料、预期输出、任务说明、目标评测和回归评测一同提供；把可写 worktree 与只读生产证据分离。agent 定位原因、跑 targeted eval 和回归集，提交候选 PR；证据含糊时回流给人。

**效果 / 结果。** 文中案例在约六周、持续人工监督下达到 90% precision/recall，并沉淀评测和审阅工件。不要将该数值外推；可迁移的结论是“反馈先结构化，再自动修复”。

### 3. GitHub Copilot：角色化 agent 与最小工具面

来源：[About custom agents](https://docs.github.com/en/copilot/concepts/agents/copilot-cli/about-custom-agents)

**有价值的点。** 可重复角色被定义为 Markdown agent profile，可声明 prompt、工具与 MCP；内置 explore、task、code-review、research、rubber-duck，说明任务边界比万能主 agent 更可维护。

**痛点。** 每轮重复讲规范和上下文会漂移；探索、执行、审查混在一个上下文会污染注意力，也让并行工作互相干扰。

**方法 / 机制。** explore 只读且可并行；task 压缩冗长成功输出；code-review 只报高信号缺陷；角色各自在独立上下文运行。自定义 profile 可以限制工具并配置专用 MCP。

**效果 / 结果。** 官方目标是复用团队规范并减少主上下文负担。个人应先从只读 `explore` 和不改代码的 `review` 两角色开始，只有任务确实独立时再引入实现子 agent。

### 4. GitHub Advanced Security：把安全检查接到 agent loop

来源：[Use GitHub Advanced Security with AI coding agents](https://docs.github.com/en/code-security/how-tos/use-ghas-with-ai-coding-agents)

**有价值的点。** 安全扫描不应只在合并后出现。GitHub 说明可通过 GitHub MCP server 让 agent 在开发中实时检查暴露 secrets，并把依赖和漏洞检查放进同一回路。

**痛点。** agent 改动快，提交前人工审查容易漏掉密钥、易受攻击依赖或不安全实现；等到远端 CI 才发现会增加返工和泄露窗口。

**方法 / 机制。** 给 agent 只读安全发现能力，将 secret scan、依赖审查、CodeQL/安全告警作为完成定义；外部写入、部署、付费调用仍要求人工确认。

**效果 / 结果。** 不能“自动保证安全”，但能把反馈前移到本地/分支阶段。**待验证：** 个人项目的覆盖与成本取决于 GitHub 计划和语言，应逐项确认。

### 5. 近期实证：真实 MCP 与配置生态

来源：[A Large-Scale Dataset of MCP Implementations on GitHub](https://arxiv.org/abs/2607.10123)；[Configuring Agentic AI Coding Tools: An Exploratory Study](https://openreview.net/pdf/ae0f92b7a4b3e8628d1c622654b9fe46d69f03bb.pdf)

**有价值的点。** 两项 2026 年研究都从公开仓库而非营销材料观察 agent 工件。前者报告 Python 与 TypeScript 占主导、混合架构常见；后者覆盖 Claude Code、Copilot、Codex、Cursor 等配置，显示 skills、subagents、commands、MCP 已成为仓库级实践对象。

**痛点。** 跨工具配置格式与运行边界不统一，照搬技能包容易造成权限和上下文膨胀。

**方法 / 机制。** 将配置、skill、MCP 当代码审阅对象：版本化、限定触发条件、列明输入/输出和权限，并为外部工具保留降级路径。

**效果 / 结果。** 研究提供生态观察，不是生产效果因果证明。**推断：** Python 适合作为分析/评测胶水、TypeScript 适合作为工具协议与交互层，是当前生态分工而非选型要求。

### 6. jcode：多会话 memory 与冲突感知协作

来源：[jcode README](https://github.com/1jehuang/jcode)

**有价值的点。** 日榜的 `jcode` 是多会话 coding-agent harness，README 展示两层记忆：语义记忆图的被动检索/周期提取，以及 agent 主动搜索/写入记忆；还声明会处理陈旧和冲突记忆。

**痛点。** 长期工作在上下文重置时遗失决定；多 agent 同时编辑时，已读文件会“在脚下变化”。

**方法 / 机制。** 记忆按相关性注入并定期 consolidation；swarm 在一个 agent 修改另一个 agent 已读文件时通知后者，允许查看 diff 和消息协调。

**效果 / 结果。** 项目宣称能降低多会话成本与冲突；README 的性能比较来自项目自身，**待验证**。可迁移实践是持久化“决策/约束/未决问题”，并将变更通知与 diff review 作为并行协作的最低保障。

### 7. Graphify：带出处与推断标签的代码库知识图

来源：[Graphify README](https://github.com/Graphify-Labs/graphify)

**有价值的点。** Python 周榜的 `graphify` 将代码、schema、文档和基础设施映射为可查询图，而不是只做向量检索；每条边标为 `EXTRACTED`（源中明确）或 `INFERRED`（解析推导）。

**痛点。** 大仓库探索依赖反复 grep/阅读，agent 容易把推断当事实，尤其跨代码、数据库和文档边界时。

**方法 / 机制。** 本地 tree-sitter AST 构建跨文件关系，输出 `graph.json`、报告和可视化，提供 query/path/explain；README 表示代码映射本地、无 LLM，而非代码资料可能需要模型/密钥语义处理。

**效果 / 结果。** “先取证、再改动”因而可执行。个人可先要求 agent 在架构结论旁列文件、符号和事实/推断标签；只在大而长期的仓库评估全图。

### 8. Orca、wigolo、Context7：并行、外网与版本化文档

来源：[Orca README](https://github.com/stablyai/orca)；[wigolo README](https://github.com/KnockOutEZ/wigolo)；[Context7 README](https://github.com/upstash/context7)

**有价值的点。** Orca 让每个 agent 在独立 worktree 中并行同一提示并比较结果；wigolo 将搜索、抓取、爬取和研究循环暴露为本地优先 MCP/REST；Context7 按版本获取源头文档，并提供 CLI+skill 与 MCP 两种接入。

**痛点。** 并行会覆盖改动；开放网络带来提示注入、非权威资料和隐私暴露；模型训练知识会产生过期 API 与幻觉。

**方法 / 机制。** Orca 用 worktree 隔离并支持评注 diff；wigolo 在 agent 附近运行 web 工具并宣称数据留在本地（该主张仍应独立审计）；Context7 用显式调用将版本化文档注入上下文。

**效果 / 结果。** 三者共同提示：并行、外网和文档都应作为有界能力接入。**推断：** 个人优先级应是版本化文档 → 只读检索 → 隔离并行；每升一级都增加来源记录、权限范围和验收证据。

## 跨来源的可操作模式

1. **任务包而非自由聊天。** 复杂工作创建任务包：目标、禁止项、可写范围、只读证据、验收命令、风险审批点。
2. **知识渐进披露且可维护。** 入口文件只作目录，架构、决策、运行、验证信息分层；关键结论记录源文件、命令与观察结果。
3. **评测和安全扫描是 agent 工具。** 优先给予 targeted test、回归、lint、浏览器检查、secret/dependency scan；失败时读证据再迭代，避免盲目重试。
4. **并行先隔离、后比较。** 一个任务一个 worktree；仅用于独立方案、可拆子任务或独立审查；合并前统一看 diff、测试和任务证据。
5. **外部工具按来源、范围、写权限分级。** 文档优先官方/版本化来源；网页/MCP 默认只读，外部写入、付费、部署、删除、提交必须人工确认。

## 个人 AI 工作流：最小 Harness

```text
Task contract → read-only exploration → plan with evidence
             → isolated worktree implementation → targeted + regression verification
             → security/diff review → human approval for irreversible actions
             → save decision, evidence, recurring failure as skill/checklist
```

建议只先落地两件低成本事项：

- 维护简短 agent 导航文件，链接架构、运行、测试、部署与安全规则，并记录验证日期。
- 为一种高频任务固定 `evidence → failing test → minimal fix → targeted test → regression → diff/security review` 清单，并保存每一步命令与结果。

## 项目含义与待验证

- **项目含义：** 后续优先建设“任务包模板”和“证据驱动复盘”，不要急于建多 agent 编排器；前两者更直接改善单 agent 可靠性。
- **推断：** 若无法在 5 分钟内说明成功证据，不应授权 agent 大范围修改，应先投资探索与可观测性。
- **待验证：** 短入口文件加分层文档是否比长指令文件降低返工；连续四周记录首次通过率、人工改回次数、查找上下文耗时。
- **待验证：** Graphify 对动态语言、生成代码和 monorepo 的关系准确性；先用小模块与手工调用图对照。
- **待验证：** 每个 MCP 的数据外发范围、提示注入防护、身份和写权限；README 不能代替安全评估。
