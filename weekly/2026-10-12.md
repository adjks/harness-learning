# Weekly Harness Notes - 2026-10-12

## 本周结论

本周的增量信号是：**把“默认会发生的 agent 行为”变成显式、可控且低噪声的生命周期机制**。GitHub 把默认模型和 MCP 自动启动拆为独立的组织/本地控制项；Cursor 的趋势插件把会话转录的学习压缩为有节流、增量索引和窄输出面的更新；`claude-mem` 则将跨会话记忆拆成采集、语义压缩和按需检索。三者都没有把“更多上下文”当作目标，而是强调在合适的时机、以受限的格式、让正确的状态重新出现。

## 本周新增资料

### 1. GitHub Copilot for JetBrains：默认模型与 MCP 自动启动应是两个独立开关

来源：[New controls and chat improvements in Copilot for JetBrains](https://github.blog/changelog/2026-10-10-new-controls-and-chat-improvements-in-copilot-for-jetbrains/)（2026-10-10）。这是本周新增的产品更新；不同于本库此前记录的 Copilot 本地 sandbox 和动态 workflow，它讨论的是**会话启动时的模型选择与工具激活策略**。

- **有价值的点**：企业管理员可以为新会话选择任意可用 agent 模型作为默认值，但仍保留显式的模型选择器；同时可关闭 Copilot 与 Claude 的 MCP server 自动启动。把“默认推理能力”和“默认能力暴露”从一个隐式环境设定，拆成可分别审计的策略。
- **痛点**：如果切换模型、启动 MCP 工具都发生在会话建立时且不可见，团队难以复现一次运行用了什么能力，也会让不需要的工具在任务开始前就获得可用性。反过来，强制每次都手动配置又会损害日常流畅性。
- **方法 / 机制**：组织级 managed settings 设定默认模型，用户仍可在模型选择器中作明确选择；IDE 增加 MCP 自动启动开关。该版本还修复了 model/provider 切换、MCP 配置、customization refresh、文件变更和 worktree 的可靠性问题，说明这些边界被当作同一个运行时控制面维护。
- **效果 / 结果**：官方宣称此举让组织能控制新对话的起点，并让用户决定何时启用已配置工具；没有公布对安全事件、延迟或成功率的量化影响，故不应把“更可控”外推为已证明“更安全”。

### 2. GitHub Trending `cursor/plugins`：将持续学习做成带节流的生命周期工作，而不是每轮自动改写指令

来源：[cursor/plugins](https://github.com/cursor/plugins)（本周 GitHub general weekly 与 TypeScript weekly；2026-10-12 检查 README），以及其中的 [Continual Learning](https://github.com/cursor/plugins/tree/main/continual-learning)、[Orchestrate](https://github.com/cursor/plugins/tree/main/orchestrate) 和 [Cursor Team Kit](https://github.com/cursor/plugins/tree/main/cursor-team-kit)。这是新发现的官方 Cursor 插件集合，入选理由是 README 所公开的工作机制，而非 stars。

- **有价值的点**：插件将可迁移的 harness 能力拆成独立包：`continual-learning` 更新持久项目事实，`orchestrate` 用 planner / worker / handoff 协调大任务，Team Kit 提供 CI 观察、声明验证、review-and-ship、smoke test 与每周复盘等小而可组合的技能。它把“让 agent 记住、并行做、最后验证”变成可安装接口，不是复制一份总提示词。
- **痛点**：从转录中持续学习容易把一次性对话、错误猜测或重复偏好写入 `AGENTS.md`；长任务的父 agent 若一直持有调度状态，则中断后难恢复，也会污染主上下文；团队常将“测试跑过”误当作“某个关键说法已被证明”。
- **方法 / 机制**：`continual-learning` 在 stop hook 后才触发，先读现有 `AGENTS.md`，只处理新增/变化的转录文件，并用本地 cadence state 与增量 transcript index 节流。默认至少 10 个完成 turn、距上次至少 120 分钟且转录 mtime 前进；产物被限制为 `Learned User Preferences` 与 `Learned Workspace Facts` 下的纯 bullet。`orchestrate` 则将任务树与 handoff 落到磁盘和 git，再由脚本调和，避免靠一个长期运行的 agent state 维系收敛。Team Kit 的 `verify-this` 要求 baseline/treatment artifact 和明确 verdict，补上“验证对象是什么”的证据面。
- **效果 / 结果**：该仓库未给出持续学习正确率、减少上下文成本或并行吞吐的独立指标；能够确认的是其公开实现具备节流、增量和窄写入面。其“增强学习/收敛”效果应视为待复现实践，而不是已证实的生产收益。

### 3. GitHub Trending `thedotmack/claude-mem`：跨会话记忆必须压缩、可检索，并与原始执行记录区分

来源：[thedotmack/claude-mem](https://github.com/thedotmack/claude-mem)（本周 GitHub general weekly 与 TypeScript weekly；2026-10-12 检查 README）。仓库本周仍有提交；这是一项首次纳入的趋势资料，而非对本库此前 Copilot Memory 或 TencentDB Agent Memory 的重复。

- **有价值的点**：它把 session continuity 实现为“自动捕获 tool-use observation → 生成 semantic summary → 在未来 session 提供检索”的三段式管线。这个拆分提醒我们，原始执行日志、为模型压缩的记忆、以及给人审计的结论不应是同一份文档。
- **痛点**：会话结束或重连会丢失项目上下文；若直接把完整历史塞回提示词，既昂贵又会让过期、错误或无关信息影响下一次决策。
- **方法 / 机制**：README 将其定位为 Claude Code 的 persistent memory compression system，并提供 MCP search tools 与配置入口；记忆由工具调用观察和语义摘要构成，供后续 session 检索。它的架构因此倾向于“存储较全，注入较少”，而非“每次加载全部历史”。
- **效果 / 结果**：仓库声称可在 session 结束或重连后保持项目知识连续性；本次未找到独立的正确率、遗忘率、隐私泄漏率或 token 节省评测。尤其是自动捕获工具观察是否包含敏感命令输出、摘要如何过期，仍须在启用前验证。

## 跨来源实践模式

1. **把默认值视为权限策略的一部分**：默认模型、自动启动的 MCP、自动写入记忆都改变一次会话的实际能力面。它们应有拥有者、可见状态、明确覆盖规则和撤销路径。
2. **记忆写入要比记忆读取更保守**：先以增量索引筛选候选事实，再将结果限制到小型、可审阅的结构化位置；不要把整段对话直接升级为长期规则。
3. **控制状态落在耐久介质上**：大任务的计划、handoff、执行证据和 stop reason 应写入文件、git、任务队列或 trace，而不是仅存在调度 agent 的上下文中。
4. **“验证”应输出 verdict 与工件**：测试命令的退出码、baseline/treatment、所验证的主张与结论要关联起来；否则下一轮 agent 只能看到“跑过一些命令”，不能判断工作是否真的完成。

## 对个人 AI 工作流的建议

- 建一个最小的启动清单：`task model`、允许自动启动的工具、可写入的位置、需要人工确认的动作；每一项都能在任务产物中回看。
- 对 `AGENTS.md` / 长期记忆实施“双门”：先写到候选条目或本地变更，再由你或独立 verifier 合并。只有跨任务稳定、可被仓库事实支持的内容才进入项目级规则。
- 对超过一个会话的任务保存 `plan.md`、`handoff.md` 和 `evidence/`，并记录当前 owner、下一步、阻塞点、已运行命令与结果。这样即便更换模型或中断，也无需重建整个对话状态。
- 对 “已完成” 使用一个很小的 verdict 模板：`主张`、`证据命令/工件`、`结果`、`残余风险`。没有证据就写“未验证”，不要让自然语言总结代替验收。

## 对项目的含义

本仓库后续可以把 memory、policy 和 verification 的资料按“写入触发—持久层—读取/注入—过期/撤销—证据”统一标注。现有周报已讨论记忆和权限；本周补足的是两个容易遗漏的接口：**默认行为的显式开关**与**低噪声的记忆写入节流**。这有助于比较不同工具时不只看“有没有 memory/MCP”，还看它们什么时候动作、由谁控制、如何恢复和如何审计。

## 推断与待验证

- **推断**：对于个人项目，“每 10 个完成 turn 或每 120 分钟”未必是最佳节流阈值；更合适的触发信号可能是任务关闭、重复失败、或验证 verdict 改变。需要用误写入率与人工审阅耗时来校准。
- **待验证**：关闭 MCP 自动启动是否实际降低了越权/泄露风险，取决于工具授权、启动后的权限、以及用户是否会随即手动启动；产品公告未提供安全实证。
- **待验证**：`claude-mem` 的自动 observation 捕获、摘要、检索与删除策略是否适合含密钥、客户数据或生产日志的项目。采用前需单独检查存储位置、过滤规则、访问控制与清理能力。
