# Weekly Harness Notes - 2026-08-17

## 本周结论

本周新增资料把注意力从“如何让更多 agent 同时运行”拉回到一个更工程化的问题：**谁拥有调度状态、隔离边界、证据和恢复语义**。OpenAI 的 Symphony 将 issue tracker 变为控制平面；Agents SDK 将沙箱、快照和外置状态变为运行时能力；GPT-5.6 的工程复盘则给出了一条容易被忽视的经济约束——agent loop 中每一项重复成本都会被多轮工具调用放大。实验项目 MemoHarness 补充了另一面：若要让 harness 从经验中变化，应把可调控制面和结果标注拆开，而不是把所有经验塞进一个更长的 prompt。

对个人工作流而言，最值得先采用的是一份小型、可版本化的任务合同：`任务状态 → 独立工作目录 → 验收命令/证据 → 人工交接状态 → 重试与停止条件`。并行度是这套合同稳定之后才该增加的变量。

### 1. `openai/symphony`：把任务看板变成 agent 的控制平面

来源：[OpenAI: An open-source spec for Codex orchestration: Symphony](https://openai.com/index/open-source-codex-orchestration-symphony/)，[Symphony Service Specification](https://github.com/openai/symphony/blob/main/SPEC.md)，[仓库 README](https://github.com/openai/symphony)。这不是对先前 OpenAI Harness Engineering 的重复：前者说明“agent-first 团队如何工作”，本资料给出了一个语言无关的、可实现的长期编排服务规范。

**有价值的点。** Symphony 的关键迁移是以 issue 而非交互式会话为中心：每个 active issue 对应一个隔离工作区和 agent run，工程师管理任务状态与交付物，而不是在多个终端里追踪会话。官方案例称部分团队的落地 PR 数提升 500%；这属于作者报告的团队结果，不能直接外推给小团队。

**痛点。** 多开 agent 后真正稀缺的是人的上下文切换能力：谁在做什么、何时已停滞、是否仍有资格执行、重启后从哪里继续，若靠人工盯终端，很快成为新的瓶颈。

**方法 / 机制。** 规范把责任拆为可替换层：仓库内版本化的 `WORKFLOW.md` 策略、带类型校验的配置、issue adapter、唯一的 orchestrator 状态、按 issue 确定性创建并保留的 workspace、agent runner、结构化日志与可选状态面。调度端有固定轮询、并发上限、状态再协调、失效 issue 的主动停止、指数退避和启动恢复；成功的终态可以是 `Human Review`，并不等于 `Done`。这明确了 scheduler 与 agent 的边界：编排器负责资格、隔离和恢复；agent 在受控工具内执行评论、PR 链接或状态写入。

**效果 / 结果。** 机制的直接效果是让“崩溃/暂时失败/任务失去资格”成为可观测状态转移，而非隐含在聊天记录里。规范同时声明它是面向可信环境的 engineering preview，且不强制统一审批或沙箱策略；因此部署者仍须自行定义权限、凭据与人工确认。

### 2. OpenAI Agents SDK：把 sandbox、状态与计算分开，才有可恢复的长任务

来源：[The next evolution of the Agents SDK](https://openai.com/index/the-next-evolution-of-the-agents-sdk/)。这是对本库既有 Codex App Server 资料的新增补充：它把此前偏产品接口的 harness 能力具体化为 SDK 的沙箱编排、Manifest 和状态恢复边界。

**有价值的点。** SDK 将文件系统工具、shell、`apply_patch`、MCP、skills、`AGENTS.md` 与可配置记忆收拢为一个可定制 harness，同时强调将 harness 控制面与执行代码所在的 sandbox 分离。长任务不应把“容器还活着”当作唯一状态来源。

**痛点。** agent 需要读写文件、装依赖和运行代码，但把凭据、任务状态和模型生成代码放在同一环境，会同时增加提示注入/外泄风险与容器失效后的恢复成本；开发者也容易把各家 sandbox、挂载和工件约定拼成不可迁移的私有脚本。

**方法 / 机制。** 原生 sandbox 为运行代码提供受控工作区；Manifest 描述本地挂载、输出目录和对象存储输入，使工作区配置可在 provider 间迁移。官方进一步建议状态外置，并以快照/rehydration 从 checkpoint 恢复失效或过期的容器；需要并行时，可按任务分派到隔离 sandbox，而非共享同一执行环境。

**效果 / 结果。** 这降低了构建长程执行环境的集成工作，并使“更换容器”不必等同“丢失任务”。其效果依赖应用实际将进度、证据和身份信息外置；只使用 sandbox 而仍把进度留在临时会话中，不能自动获得耐久性。公开客户引语是单一案例，待验证其对其他任务的可复制性。

### 3. GPT-5.6 工程复盘：性能 harness 的第一原则是缩小每轮重复区域

来源：[How GPT-5.6 fuses frontier intelligence with frontier efficiency](https://openai.com/index/gpt-5-6-frontier-intelligence-efficiency/)。这是本周新发布的实现层资料，补足此前周报侧重正确性、治理与记忆而较少讨论的成本/延迟控制面。

**有价值的点。** 一次 agent 任务会包含多次模型请求和工具调用，因此“每轮多一秒、每次多一段无关上下文、每次重新传相同工具定义”都会被循环倍增。效率不是压缩最终答案，而是降低重复路径的成本，同时保留验证闭环。

**痛点。** 工具、插件、skills 和历史不断堆叠会造成 context bloat：成本上升、模型注意力被稀释、推理变长；非确定性的工具排列或把运行时审批写进模型可见定义，也会破坏 prompt-cache 的可复用前缀。

**方法 / 机制。** OpenAI 描述了按需发现（deferred discovery）工具/插件、限制单次工具输出的默认 token 上限、将历史保持 append-only、固定工具呈现顺序，并把 approval policy 等运行时设置从工具定义中分离。文章同时说明由 GPT-5.6 Sol 参与的内核改动配合 FpSan 做正确性验证，说明高杠杆优化也要有独立 oracle，而非以吞吐数字替代正确性。

**效果 / 结果。** 文中称生产服务端到端成本下降 20%、speculator 改进使 token 生成效率提升逾 15%，均是 OpenAI 自身生产系统数据。可迁移到个人环境的结论并不是追求同样数字，而是：让默认上下文与工具集尽可能窄、稳定；把权限等控制放在运行时；只在任务需要时加载扩展，并对长输出设置预算与截断策略。

### 4. `MemoHarness`：从“经验”学习时，先把 harness 的可调面和证据面分开

来源：[HowieHwong/MemoHarness README](https://github.com/HowieHwong/MemoHarness)，论文：[MemoHarness: Agent Harnesses That Learn from Experience](https://arxiv.org/abs/2607.14159)。仓库在 2026-07-28 修复了工具遥测、trial 标注和搜索超时处理；这使其成为适合观察“自动改进 harness 如何保留实验可信度”的新资料，而非趋势热度来源。

**有价值的点。** 它不试图改 base model，而是把 harness 显式拆为六个控制维度：上下文装配、工具交互、生成控制、编排、记忆与输出处理。相对于把经验浓缩进一份全局系统提示，这种拆分让改动能够被归因、检索和复验。

**痛点。** 固定全局 harness 通常无法同时适配不同任务；反复在线搜索又会增加成本并可能将测试反馈泄漏到选择过程。更危险的是，若工具遥测、结果标签或超时处理不可靠，所谓“学到的经验”会建立在错误实验记录上。

**方法 / 机制。** 项目在训练阶段搜索六维空间，保存 case-level 执行条目与 distilled global patterns 的双层经验库；测试阶段从冻结经验库检索相似案例和模式，为无标签实例选择 case-specific harness，而不是额外搜索。选择规则是先按任务正确性，再以 token 成本打破平局；其 README 还公开了 2026-07-28 的遥测、标注和 timeout 修复，便于读者判断实验数据的时间边界。

**效果 / 结果。** README 展示 FinanceAgent 从 42.5% 升至约 65.0% 峰值、LiveCodeBench 近乎饱和的曲线；这些是项目作者报告，且不同任务的结果并不一致。对个人最实用的借鉴是：每次调 prompt、工具或流程时都记录任务类别、配置、验收结果、耗时/成本与失败原因；没有可靠 telemetry 的“自动优化”应标为待验证。

## 跨来源实践模式

1. **先让任务系统成为事实源，再把会话当作执行细节。** Issue 状态、当前 owner、工作目录、重试原因和交接状态应在聊天之外可查询；会话可以丢失，任务合同不应丢失。
2. **隔离与耐久性需要同时设计。** 每项工作一个目录/沙箱限制误操作影响面；外置 checkpoint、工件和证据解决容器失效后的继续执行。只做其中一项都不完整。
3. **把“运行时控制”从“模型上下文”剥离。** 权限、并发、token/输出预算、重试和停止条件由 harness 强制；只有任务相关的事实、约束和工具说明进入模型可见上下文。
4. **自动改进必须有实验账本。** 配置变更、可观测结果、超时、失败和版本一起记录；先以正确性筛选，成本只能作为次级优化目标。
5. **人工 review 是合法终态。** 对高风险、需求含糊或外部写入任务，`Human Review` / `Needs Decision` 比“为了闭环而自动 Done”更可靠。

## 对个人 AI 工作流的建议

- 为跨会话任务增加一个轻量状态文件或 issue 字段：`状态、当前 next step、工作目录、验收命令、最新证据、允许重试次数、人工闸门`；只要这些字段缺失，就不要扩展到并行 agent。
- 每个 agent 的工作目录独立，产物与测试日志写回固定位置；恢复任务时先读取状态和证据，不从完整聊天历史开始猜测。
- 把默认 MCP/skills/工具输出保持精简并稳定；需要专项能力时再按需加载，避免“常驻全量工具箱”。
- 做 workflow 调整时使用小型对照表：任务类型、版本/配置、通过的 oracle、耗时、token/费用、失败模式；连续若干次无证据改进即停止调整。
- 对 push、发布、生产写入、需求解释和不可逆操作，明确配置为人工交接，而不是让 scheduler 将无响应等同成功。

## 对项目的含义

后续知识库可将每个实践案例以统一字段记录：`控制平面 / 任务事实源 / 工作区隔离 / 耐久状态 / 验收 oracle / 运行时预算 / 人工终态 / 遥测与复现实证`。这能同时区分产品能力、规范要求、作者案例和独立实验，避免将“可并行”误读为“可无人值守”。

## 推断与待验证

- **推断：** 对个人开发，先实施 per-task 状态和工作目录隔离，往往比立刻加入复杂 supervisor 更能降低恢复成本；四份资料的机制一致，但没有针对个人开发者的受控比较。
- **待验证：** Symphony 的 500% PR 增长为部分团队的官方报告；实际收益会受 issue 质量、CI 时间、review 容量、权限模型和任务依赖限制。
- **待验证：** Agents SDK 的 sandbox/rehydration 只有在进度、凭据与工件确实外置时才带来可恢复性；需要针对具体 provider 和权限配置演练失效恢复。
- **待验证：** GPT-5.6 的成本与效率数据来自 OpenAI 内部生产系统，个人仓库应先测量自己的上下文、工具调用和 CI 成本，不能直接套用百分比。
- **待验证：** MemoHarness 的收益依赖任务分布、基模型和实验协议；其遥测修复提醒我们先审计记录质量，再相信自动优化曲线。
