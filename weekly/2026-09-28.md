# Weekly Harness Notes - 2026-09-28

## 本周结论

本周的新增资料把一个容易被混淆的边界讲清了：**让 agent 有记忆、并发和更多自主性，并不等于把完成判定也交给它。** 可持续的 harness 应让每轮执行都留下可重放的 trace、每一项权限在真实环境中可拒绝地执行、每个“已确认”的安全/修复结论有独立证据，而把长期记忆限制为可审计、可失效和可纠正的输入。成本控制也不应粗暴地在一次长会话中频繁换模型；缓存属于一个会话，路由应放在会话开始、旁路任务或子 agent 启动等天然边界。

### 1. GitHub Copilot：本地 sandbox、OTel trace 与修复记忆形成“可限制、可观察、可回溯”的执行闭环

来源：[Local sandboxing in the GitHub Copilot app](https://github.blog/changelog/2026-09-23-local-sandboxing-in-the-github-copilot-app/)（2026-09-23）、[OpenTelemetry in the GitHub Copilot app](https://github.blog/changelog/2026-09-22-opentelemetry-in-the-github-copilot-app/)（2026-09-22）、[Agentic autofix now uses Copilot Memory](https://github.blog/changelog/2026-09-25-agentic-autofix-now-uses-copilot-memory/)（2026-09-25）。

- **有价值的点**：三项更新正好覆盖 agent run 的三个不同层次：启动时可申请的文件、网络和凭据边界；运行中可导出的模型/工具 span；完成后可供下一次安全修复读取的仓库专属模式。它们不是一份更长的 prompt，而是分别落在 OS policy、开放遥测标准和有生命周期的 memory 上。
- **痛点**：本地 agent 若只靠“请勿越界”的提示，就无法证明 shell 是否真的被隔离；没有 trace 时，出错后无法区分模型、工具、权限或环境问题；每个安全告警又从零开始，会重复已经验证过的项目惯例。
- **方法/机制**：Copilot app 的 project sandbox 分别声明额外 read/write、read-only 与 deny folders，外网/局域网和 Git/GitHub CLI 凭据；企业策略还能收紧其 effective policy，OS 无法强制时 shell 直接失败而非降级裸跑。OTel 用 enterprise `managed-settings.json` 集中配置 endpoint，默认不导出 prompt/response 内容，但会导出会话中的模型请求和工具使用 span。启用 Copilot Memory 后，agentic autofix 先读取已有 memory，创建修复时再写入 fix pattern，并可让 code review/cloud agent 复用。
- **效果/结果**：官方没有给出越权率、排障时间或修复成功率的比较；三项能力均含 preview 成分，故效果**待验证**。但可立即复刻的最小实践是：每次 run 同时保存 `effective-policy`、无敏感正文的 action trace 和一个带来源/适用范围/失效条件的 `fix-pattern`，而不是只保存 agent 最终说了什么。

### 2. Google Cloud Agent Factory：把 loop、tool 与 memory 当成三个显式设计变量，并让 verifier 决定 loop 的停止

来源：[Agent Factory recap: Agent harnesses, shifting left, and autonomous coding](https://cloud.google.com/blog/topics/developers-practitioners/agent-factory-recap-agent-harnesses-shifting-left-and-autonomous-coding)（2026-09-25）。

- **有价值的点**：文章把“定制 harness”压缩为三个可审查问题：最多循环几次和何时退出、开放哪些工具及调用条件、何时检索/压缩对话与操作记忆。对于需修复的任务，闭环不是让模型自评，而是 harness 跑 unit tests，把失败日志和 stack trace 送回下一轮。
- **痛点**：一方面把所有任务交给自由循环会产生无限重试和成本失控；另一方面为每个模型写一套庞大框架，模型升级后会变成技术债。长调试又会被历史对话挤占上下文。
- **方法/机制**：对检查、文件转换等确定任务使用 single-pass linear harness；对 bugfix/refactor 使用 edit → test → failure diagnostics → next turn 的 closed loop，并设置五轮上限。文章还示例以 context compaction 管理旧轮次、以 pre-execution hook 拦截递归删除、drop database、未授权 remote push；建议把会随模型演进而增值的知识放入工具、确定性 verifier 和精炼 context，而非锁死在 bespoke orchestration 中。
- **效果/结果**：闭环 demo 会在 unit tests 通过或达到 5 次上限时停下，因此其停止条件可复现；文章并未给出在真实团队中的 defect/cost 对照，**待验证**。对个人工作流的直接含义是：任务类型先决定 loop 形态，且每个循环必须写明 `oracle command`、`max_attempts` 与 `on_exhausted`，不能只设置 token budget。

### 3. 论文《Control the Harness, Control the Cost》：缓存感知的路由应发生在会话边界，而不是每个 agent step

来源：[Control the Harness, Control the Cost: Routing and Governing AI Coding Agents in the Enterprise](https://arxiv.org/abs/2609.28919)（预印本，2026-09-24）。

- **有价值的点**：作者指出一个 coding-agent turn 是同一模型 prompt cache 上的多次请求，因此“每步挑最便宜模型”的 chat-router 直觉常常错误：中途切换要重建 cache。论文将路由点限定为 session start、side lane 与 subagent launch，正好与个人 harness 能明确切分工作的边界一致。
- **痛点**：长而 tool-heavy 的会话若只看单 token 标价，会漏掉 cache 写入与重建；另一端，完全锁定单一 vendor/model 又会带来成本、技能/connector 碎片与可替代性风险。
- **方法/机制**：用价格表推导“中途切换需节省多少才回本”的规则，并让快速分类器按自带任务 taxonomy 给出校准概率；只在新会话或独立子任务启动时选择模型。作者还提出从 vendor defaults、可配置、到由 gateway/telemetry/policy floor/taxonomy 支撑的 controlled 层级，用于区分“能设置”与“能测量并治理”。
- **效果/结果**：以公开数据集约 10,000 个真实 session 重定价、再模拟 10,000-seat enterprise，作者报告 14–21% 模型支出节省；其中长会话的结果严重依赖所用价格、cache 期限、任务分类与仿真假设，不能外推为个人节省承诺，**待验证**。可迁移结论是记录 session 的模型、cache/上下文代价、任务类型与结果，并优先把低风险检索、格式化或验证拆为独立 side lane，再决定是否采用便宜模型。

### 4. GitHub Trending `cloudflare/security-audit-skill`：以 coverage ledger 和独立反证把“agent 发现”变成可审计 verdict

来源：[cloudflare/security-audit-skill](https://github.com/cloudflare/security-audit-skill)（本周 GitHub Trending general weekly/Python weekly；README 于本周检查）及其中链接的 [Build your own vulnerability harness](https://blog.cloudflare.com/build-your-own-vulnerability-harness)。

- **有价值的点**：该仓库将 Cloudflare 的漏洞发现 harness 缩成一个可在单仓库采用的 skill：不是让多个 agent 竞相输出漏洞清单，而是先量化覆盖、再独立验证候选、最后对记录再次独立验真。它把“未证实”保留为一等状态，而不是为了完整报告强行给 severity。
- **痛点**：多 agent 审计常发生重复 hunting、覆盖盲区不可见、一个 agent 自己提出并确认同一结论、报告把猜测当发现；多次执行还容易把旧证据错误当作对新代码的覆盖。
- **方法/机制**：六阶段为 reconnaissance（产出 `architecture.md` 与 `coverage-ledger.json`）→ coverage-led hunting（从 ledger 切分隔离 hunter，并用 critic 找空白）→ fresh verifier 尝试否证每一独特候选 → 将 `confirmed`/`needs_validation`/`rejected` 写入 `findings.json` 并经 JSON schema 校验 → fresh agent 验证最终 source claim，重大替换再复验 → 从已验证记录和 ledger 派生报告。父流程在每次 ledger 更新后运行 coverage validator，在记录生成/替换后运行 findings validator；重复运行只增量覆盖空白、重验变更源，不把 stale/unresolved 当已覆盖。
- **效果/结果**：README 未发布误报率、真实漏洞数或人工节省的独立基准，不能以“Cloudflare 同源”推断个人审计效果，**待验证**。但 verdict 分层、独立反证与机器可读 ledger 是可直接迁移的：将任意高风险 agent 输出设为 `claim → evidence → fresh verifier → status`，且 `needs_validation` 不触发自动修复或发布。

### 5. GitHub Trending `strands-agents/harness-sdk`：把 agent loop 的可中断性和 stop reason 提升为 SDK 级契约

来源：[strands-agents/harness-sdk](https://github.com/strands-agents/harness-sdk)（本周 GitHub Trending Python weekly；README 于本周检查）。

- **有价值的点**：该项目明确面向“否则就会自己写 agent loop”的场景，且强调 in-process、无需 hosted control plane。README 将 turn limits、token budgets、cancellation 与 stop reasons 与 tools、MCP、sessions/memory、guardrails、tracing、evals 并列，而不是把失败控制视为应用层补丁。
- **痛点**：手写 loop 往往先能调用模型和工具，随后才逐步补上取消、超限、结构化输出、session、观测和 evaluation；这些零散补丁会使不同任务的停止语义不一致，也难以比较失败原因。
- **方法/机制**：Python/TypeScript SDK 与 `create_harness()` 将生命周期控制、模型可移植性、MCP、多 agent 模式及 observability/evals 组合为可选能力。它并不要求所有任务使用完整平台，因此可把“为什么停止”作为 harness 的统一结果字段：完成、验证失败、达到轮数/预算、取消、策略拒绝或环境故障。
- **效果/结果**：这是项目 README 的能力声明，未见本周可复查的生产效能对照；**推断**：统一 stop reason 能降低人类在失败 run 之间的诊断成本。验证方式是在同一任务集统计各终止原因、重试后成功率和不必要的重复调用，而不是以 SDK 接入速度作结论。

## 跨来源实践模式

1. **把 run 设计成证据对象，而非聊天记录。** 最小 run record 至少关联 task/spec、effective policy、工具/模型 trace、独立 verifier 结果、stop reason 和产物版本；正文可脱敏或不采集。
2. **循环的 owner 是 verifier。** linear inspection、closed-loop repair 与多 agent audit 可共用一条原则：harness 根据外部 oracle、覆盖状态或轮数上限决定继续/停止；模型不能既提出 claim 又单独裁决成功。
3. **长期 memory 只能作为可撤销输入。** 将仓库专属 fix pattern、coverage ledger 和 context summary 都保存来源、适用路径、创建时间、最后验证 commit 与失效条件；代码变更后优先重验，不把旧经验提升为永久事实。
4. **并发和换模型应顺着天然边界发生。** 先切分有独立输入/验收的 side lane 或 subtask，再给其选择模型、预算和隔离环境；保持一条长会话的 cache/上下文连续性，避免按每个 step 震荡路由。
5. **自建的重点是 policy/oracle/telemetry seam，不是重写基础 loop。** 对个人和小团队，先用成熟 runtime 的文件、搜索、命令与会话能力；只把项目特有的 deny list、验收命令、证据 schema 和调度规则沉淀为版本控制资产。

## 对个人 AI 工作流的建议

- 在任务模板中加入 `run.json`：`task_id`、输入 commit、允许目录/域名、工具调用摘要、验证命令、`stop_reason` 与人工接受人；trace 仅留 metadata，敏感输入默认不收集。
- 将“修复经验”写成带 `source_commit`、`scope`、`expires_on_change` 的短记录。下次 agent 可检索它，但必须在当前代码上重跑对应测试才能标为 `revalidated`。
- 每一个 repair loop 都设置外部 oracle 与二次退出：例如 `pnpm test --filter X`、最多 3 次；到上限时产出 failure bundle 并交给人，而不是继续让 agent 试到耗尽预算。
- 高风险 review/security 任务采用两个角色：hunter 只形成带证据的 candidate，fresh verifier 专门尝试反证；无完整 source trace 的输出保持 `needs_validation`。
- 仅在新 session 或真正独立的子任务启动时换模型。先记录基线的 token、时长和成功率；没有成本/质量数据，不要为“理论最便宜”破坏长会话连续性。

## 对项目的含义

本库的 CodeGuard/个人 harness 适合优先实现一个只追加的 `run ledger`，而不是再做一个新的 agent runtime：它接收 policy manifest、命令结果、trace metadata、artifact hash 和统一 `stop_reason`。在此之上将 review/security claim 设计成 JSON schema，状态限定为 `confirmed`、`needs_validation`、`rejected`；只有 `confirmed` 且 freshness 校验通过，才允许进入自动化后续动作。这样能把上周提出的 `effective_policy.json` 与 converge report 连接成同一份可审计 run 证据。

## 推断与待验证

- **待验证**：Copilot Memory 让 agentic autofix 复用 fix pattern 是否降低重复安全告警的处理时间，还是会把过期/错误模式扩散；应按 memory 命中后再次验证通过率、回滚率和过期记录命中率衡量。
- **待验证**：论文的 14–21% 路由节省依赖企业仿真和特定价格/缓存假设；个人 harness 应先比较“整段会话固定模型”与“边界路由”两组 run 的端到端成本及验收通过率。
- **推断**：将 shell-policy failure 视为正确的 fail-closed 结果，会比无 sandbox 时继续执行更能降低静默越界；需要统计因平台不支持导致的阻断率和安全收益，避免把可用性问题隐藏成安全策略。
- **待验证**：独立 verifier 能减少多 agent 审计的误报，却可能带来延迟和成本；可用 sample-based human adjudication 对比 verifier 前后 precision、coverage gap 和每项 confirmed 的人机耗时。
