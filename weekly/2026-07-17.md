# Weekly Harness Notes - 2026-07-17

## 本周主题

这周重新校准仓库方向：重点不是记录我自己的 AI 使用流水账，而是收集网络上大家如何 **Harness 驾驭 Agent** 的实践，再提炼为可迁移到个人工作流的模式。

这篇周报的阅读方式：每个资料都按四个问题拆解：

- 它提出了什么有价值的点？
- 它针对的痛点是什么？
- 它用了什么方法？
- 它产生了什么效果，或者声称能产生什么效果？

## 本周资料详解

### 1. Claude Code best practices

来源：[Claude Code best practices](https://code.claude.com/docs/en/best-practices)

**有价值的点**

这篇资料最有价值的地方是把 coding agent 工作流拆成清晰阶段：Explore -> Plan -> Implement -> Commit。它不是把 agent 当成“马上写代码的工具”，而是把 agent 放进一个带阶段边界的 harness 里。

**痛点**

直接让 agent 开始编码，很容易出现“解错问题”：agent 可能没读够上下文、误解架构边界、修改了不该修改的文件，或者实现了一个看似合理但不符合项目约定的方案。

**方法**

- 先进入 Plan Mode，让 agent 只读探索代码、配置、约定和相关模块。
- 再让 agent 生成详细实现计划，列出文件范围、数据流、测试方式和潜在风险。
- 用户可以先编辑或批准计划，再切回实现模式。
- 实现阶段要求 agent 按计划改动，并写测试或运行验证。
- 最后再处理 commit/PR，而不是把提交动作混在模糊实现请求里。

**效果**

这个模式的效果是降低“方向性错误”。它让 agent 在修改前先暴露自己的理解，使人可以用较低成本纠偏。对个人工作流来说，这是一个很强的默认规则：凡是跨文件、陌生代码、架构相关、影响长期维护的任务，都应该先探索和计划。

### 2. Claude Code power user tips

来源：[Claude Code power user tips](https://support.claude.com/en/articles/14554000-claude-code-power-user-tips)

**有价值的点**

这篇资料把 verification 明确放在第一位：如果只采用一个实践，就让 agent 能验证自己的输出。它还把并行 worktree、plan mode、skills、subagents、hooks、permissions、scheduled tasks 等能力放在一个完整的 power-user 操作面里。

**痛点**

agent 生成内容不难，难的是知道它是否真的正确。没有反馈回路时，agent 只能“看起来完成了”；对前端、重构、长期任务、PR review 等场景尤其危险，因为错误经常不在单个文件里暴露。

**方法**

- 给 agent 可执行验证器：测试、lint、浏览器、模拟器、端到端脚本、截图、日志查询。
- 对前端任务，让 agent 使用浏览器观察真实页面，而不是只读代码想象 UI。
- 对重复流程沉淀 skills，把高频任务变成可复用能力。
- 对 PR 和代码质量使用 subagents 或 review agents，从不同角度交叉审查。
- 对长任务使用 hooks、schedule、loop 或后台 agent，让检查流程不依赖人一直盯着。
- 对权限使用 pre-approval、sandbox、auto mode 等方式，把安全动作和高风险动作分开。

**效果**

资料声称最显著的质量提升来自 verification：agent 可以自己闭环迭代，直到输出满足检查。对个人使用者的启发是，与其追求更神奇的 prompt，不如先建设“验证环境”：能跑测试、能看页面、能查日志、能比较 diff、能复盘失败。

### 3. Claude Code common developer use cases

来源：[Claude Code common developer use cases](https://support.claude.com/en/articles/14553517-claude-code-common-developer-use-cases)

**有价值的点**

这篇资料不是抽象原则，而是把 agent 放进软件开发生命周期：发现、设计、构建、部署、支持和扩展。它展示了 agent 在修失败测试、理解陌生代码、triage 错误、按计划重构、补测试、review PR、onboard 新仓库、处理 issue、创建 skill 等场景中的具体入口。

**痛点**

很多人使用 agent 的问题是入口太散：每次都临时问一句，导致上下文、目标和验收标准不稳定。另一个痛点是开发任务并不总是“写新代码”，很多价值来自理解、定位、补测试、review 和维护。

**方法**

- 针对失败测试，让 agent 读测试、追踪被测模块、修复后重跑测试。
- 针对陌生代码，让 agent 先解释模块、入口、调用链和项目约定。
- 针对多文件重构，先用 plan mode 生成修改清单，批准后再动手。
- 针对补测试，让 agent 对齐现有测试风格，并运行测试确认。
- 针对 PR review，让 agent 拉取 diff、评论和 CI 状态，再结合仓库上下文审查。
- 针对新仓库 onboarding，用 `/init` 或类似机制生成项目记忆文件。
- 针对重复任务，把流程写成 skill。

**效果**

它的效果是把 agent 从“代码生成器”变成“开发生命周期助手”。个人可以从这里抽一个实用清单：遇到问题时先判断任务类型，再选择对应 harness，而不是所有问题都用同一种 prompt。

### 4. OpenAI: Harness engineering

来源：[OpenAI: Harness engineering](https://openai.com/index/harness-engineering/)

**有价值的点**

这篇文章提出了很强的工程视角：在 agent-first 的软件生产里，人类的主要工作从“亲手写代码”转向“设计环境、指定意图、建立反馈回路”。它把核心原则概括为：Humans steer. Agents execute.

**痛点**

agent 初期不是因为不会写代码而慢，而是因为环境欠规格化：缺少工具、抽象、脚手架、可读日志、可执行检查、项目内规则和可供 agent 理解的应用状态。另一个痛点是人类注意力成为瓶颈，尤其是 QA、review 和上下文搬运。

**方法**

- 从空仓库开始，让 Codex 生成项目结构、CI、格式规则、测试、文档、工具和 AGENTS.md。
- 把大目标拆成设计、代码、review、测试等小块，深度优先搭出 agent 可用的能力。
- 当 agent 失败时，不是简单“再试一次”，而是问：缺了什么能力？如何让它对 agent 可读、可执行、可约束？
- 让 Codex 使用标准开发工具，例如 `gh`、本地脚本和仓库内 skills，而不是靠人复制粘贴上下文。
- 让应用 UI、日志、metrics、traces 对 agent 可读：例如每个 worktree 可启动独立应用实例，接入浏览器/DevTools、LogQL、PromQL。
- 把风格、质量和约束编码成文档、lint、脚本和工具，让规则进入 agent 的工作环境。

**效果**

文章声称他们以约十分之一的手写时间构建并交付了一个内部产品，约 1500 个 PR 被打开和合并。更重要的启发不是这个数字，而是方法论：要提升 agent 产出，不只是换更强模型，而是让项目本身变得对 agent 可读、可测、可恢复、可审查。

### 5. VS Code: The Coding Harness Behind GitHub Copilot

来源：[The Coding Harness Behind GitHub Copilot in VS Code](https://code.visualstudio.com/blogs/2026/05/15/agent-harnesses-github-copilot-vscode)

**有价值的点**

这篇文章直接解释了“coding harness”到底做什么：组装上下文、暴露工具、执行工具调用、运行 agent loop、压缩历史、处理不同模型差异。它把模型能力和产品体验之间的中间层讲清楚了。

**痛点**

语言模型本身只能输出文本，不能真正编辑文件、运行命令、读工作区或执行测试。如果没有 harness，模型输出无法可靠转化成工程动作。另一个痛点是不同模型的 tool calling、结构化输出、推理控制、上下文长度和错误行为都不一样，不能假设“一套 prompt 适配所有模型”。

**方法**

- harness 在请求前组装 prompt：系统消息、用户问题、工作区结构、打开文件、历史对话、工具结果、自定义指令和记忆。
- harness 声明工具及其 JSON schema，例如读文件、编辑代码、运行终端、搜索代码库。
- harness 执行工具调用，处理参数校验、错误、输出格式化，并把结果喂回下一轮。
- agent loop 按 think -> act -> observe -> think again 方式迭代，直到达到停止条件。
- 对不同模型调整系统 prompt、工具集和 loop 行为。
- 用工具调用限制、取消检查、stop hooks、历史摘要等机制控制循环。

**效果**

效果是让用户在 VS Code 里获得稳定一致的 agentic coding experience，即使底层模型在变化。对个人工作流的启发是：我们平时说“用哪个模型”只是表层问题，更关键的是给模型什么上下文、什么工具、什么权限、什么反馈，以及如何停止。

### 6. Anthropic: A harness for every task

来源：[A harness for every task: dynamic workflows in Claude Code](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code)

**有价值的点**

这篇资料的核心价值是把 harness 从固定工具层推进到“按任务动态生成 workflow”。它认为某些任务需要 Claude Code 在运行时写出一个专门的多 agent harness，例如研究、安全分析、代码审查、大规模迁移和复杂重构。

**痛点**

默认 coding harness 需要在同一个上下文里同时计划和执行，复杂任务很容易上下文拥挤、任务分解不充分、检查角度单一。静态 workflow 又太通用，很难覆盖每个任务的特殊边界。

**方法**

- 用 dynamic workflow 执行 JavaScript 编排脚本，动态创建和协调 subagents。
- workflow 可以选择模型、设置 subagent 是否运行在独立 worktree 中。
- 对未知工作量任务使用 loop until done，而不是固定轮数。
- 对多方案任务使用 classify-and-act：多个 agent 尝试不同方案，再用 judging agent 评估。
- 对迁移/重构任务按 callsite、失败测试、模块等维度拆分，让 subagents 并行修复，再进行对抗式 review。
- 设置 token budget，避免复杂 workflow 失控。
- 保存和分享 workflow，把经验变成团队资产或 skill。

**效果**

它的效果是把 agent 从单轮执行者提升为“任务专属执行系统”。但资料也提醒：dynamic workflow 不适合所有任务，因为会消耗更多 token 和协调成本。对个人使用者的启发是，只有当任务复杂到需要并行、分治、交叉审查或长循环时，才值得上多 agent workflow。

### 7. AgentWay: Claude Code workflows

来源：[AgentWay: Development Workflows](https://agentway.dev/en/claudecode/workflows)

**有价值的点**

这篇资料把 workflow 写成可以复制执行的提示模板，尤其适合个人学习。它覆盖 feature development、bug fix、TDD、checkpointing、PR creation 等场景。

**痛点**

很多人知道“先计划再执行”，但真正使用时缺少具体 prompt 和阶段边界。另一个痛点是 agent 试错成本：探索性重构或 bug 修复可能走错方向，需要安全回退。

**方法**

- Feature workflow：Plan Mode 探索当前系统、数据库 schema、middleware 等，再按数据库迁移、API、前端、测试分层实现。
- Bug fix workflow：先只读诊断根因，再写失败测试，最后修复并跑完整测试。
- TDD workflow：先写测试，再实现，再重构，且明确要求实现阶段不要改测试。
- Checkpointing：利用 checkpoint/rewind 在尝试失败时回退代码、对话或两者。
- PR workflow：让 agent 总结变化、测试说明、截图和 issue 链接。

**效果**

效果是把抽象原则变成上手模板。对个人工作流尤其有用：可以直接把这些 workflow 改成自己的“任务启动器”，每次遇到 feature、bug、TDD、PR，就不用重新组织 prompt。

### 8. TechRadar: governance controls for AI coding agents

来源：[Why AI coding agents keep stalling before production and the governance controls that fix it](https://www.techradar.com/pro/why-ai-coding-agents-keep-stalling-before-production-and-the-governance-controls-that-fix-it)

**有价值的点**

这篇资料从治理角度补齐了实践视角：agent 卡在生产落地，不一定是模型能力问题，而是缺少可扩展的可见性、权限和审批机制。它总结了三个关键词：isolate、scope、approve。

**痛点**

agent 自主运行速度快，权限边界如果不清楚，就可能造成数据泄露、越权访问、意外成本、不可审计操作和合规风险。对个人开发者来说，对应风险是误删文件、误提交敏感信息、跑高成本命令、修改不该修改的区域。

**方法**

- Isolate：使用临时、沙箱化环境，限制网络和工具访问。
- Scope：最小权限原则，给 agent 只够完成任务的文件、命令和外部系统权限。
- Approve：高风险动作加入人工批准，保留审计记录。
- 把治理放在基础设施层，而不是每个应用单独重复实现。

**效果**

它声称这种治理方式可以让团队更安全地扩大 agent 使用范围，同时提升开发者信心。对个人工作流的启发是：即使没有企业治理平台，也可以用 worktree、git status、明确权限、手动确认、敏感文件 ignore 和 commit 前检查来实现轻量版治理。

## 本周提炼的实用模式

### 1. Explore -> Plan -> Implement -> Verify

复杂任务先让 agent 只读探索，不要直接实现。让它输出计划、文件范围、风险和验证方式，再进入执行。

### 2. Verification first

实践资料高度一致：agent 的可靠性来自反馈回路。测试命令、浏览器检查、lint、端到端脚本、日志查询、事实核查清单，都可以作为 harness 的验证器。

### 3. Humans steer, agents execute

人的工作不是逐行写代码，而是给出意图、边界、环境和验收标准。agent 负责执行，人的重点是审计划、审证据、审风险。

### 4. Isolate, scope, approve

高自治 agent 需要隔离环境、有限权限和人工批准。个人使用时可以对应为：新分支/worktree、明确禁止事项、高风险操作前确认。

### 5. Reusable workflows

重复任务不要每次重新 prompt。把周报、PR 审查、资料核查、前端验收、发布检查做成固定 workflow。复杂高价值任务再考虑 dynamic workflow 或多 agent 编排。

## 对个人工作流的启发

可以把个人使用 agent 的入口改成一个固定问题组：

- 这次任务属于哪类：探索、修 bug、写 feature、重构、review、资料整理，还是自动化？
- 这次任务是否需要先只读探索？
- agent 需要看到哪些上下文，哪些上下文不应该给？
- 完成标准是什么？
- agent 可以运行哪些验证？
- 哪些动作必须先确认？
- 最后要留下什么证据？

更具体的轻量 harness 可以这样搭：

- **任务契约**：目标、范围、禁止事项、验收标准。
- **隔离环境**：分支或 worktree。
- **验证器**：测试、lint、浏览器、日志、截图、事实来源。
- **审批点**：删除、部署、外部写入、提交、付费 API。
- **复盘记录**：失败原因、缺失上下文、下次应固化的规则。
