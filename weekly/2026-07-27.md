### 1. OpenAI：Codex App Server 将 agent 会话变成可嵌入的事件协议

来源：[Unlocking the Codex harness: how we built the App Server](https://openai.com/index/unlocking-the-codex-harness/)

**有价值的点。** 文章把“相同 agent loop 如何服务 CLI、IDE、Web 与桌面端”讲成了一个具体边界：核心运行时负责单线程会话、配置/认证、受策略约束的工具调用；App Server 则用双向 JSON-RPC 把它们向客户端暴露。一次用户请求不是单一 HTTP 返回，而是一串可渲染的输入、进度、工具调用、diff、审批请求和最终产物事件。

**痛点。** 把 agent 只包装成 `prompt -> response` 会丢失长任务最重要的状态：现在在做什么、是否卡在工具、哪一步改变了文件、何时必须由人批准。不同客户端各自重写 loop 还会让权限、线程恢复和行为语义漂移。

**方法 / 机制。** 用长期运行的 server 承载多条 core thread；以稳定、面向 UI 的通知替代内部低层事件；当工具动作需要批准时，server 主动发起请求并暂停本轮，直到客户端 allow/deny。MCP 可参与扩展，但文中说明 IDE 所需的丰富双向交互并不自然等同于 MCP，因此选择明确的 JSON-RPC 应用协议。

**效果 / 结果。** 这是将同一 harness 复用于不同表面的工程方案，而不是“再做一个聊天界面”。可迁移的结果是：任务即使中断，也应能从事件和工件恢复；审批也应是可见状态转换，而非聊天文字里的模糊约定。

### 2. OpenAI：安全治理应按动作风险分层，而非一律阻断

来源：[Running Codex safely at OpenAI](https://openai.com/index/running-codex-safely/)

**有价值的点。** 文中把 sandbox、审批、网络、身份凭据、规则和 agent-native telemetry 组合为一个控制面。关键原则是：低风险、日常开发动作应顺畅；越出边界、影响外部系统或后果难撤销的动作必须升级审查。

**痛点。** “完全放开”把网络、凭据和写入风险交给 prompt；“每个命令都审批”又会把人变成吞吐瓶颈。两种极端都不适合长期自动化。

**方法 / 机制。** sandbox 声明可写路径与网络边界，approval policy 决定跨边界时何时暂停；网络按允许域名/陌生域名批准管理；凭据置于操作系统密钥环；规则按命令类别区别对待；保留可审计的 agent 原生日志。文中还给出 auto-review 作为可基于计划动作和近期上下文降低低风险打断的机制。

**效果 / 结果。** 文章主张的效果是同时保持开发速度与审计能力；它不是“自动批准就安全”的证明。个人工作流可直接采用三层：默认只读探索、工作区内可逆编辑、外部写入/部署/删除/付费调用必须人工批准，并在任务记录中保留命令与审批理由。

### 3. `code-review-graph`：结构图谱为 agent 提供“变更爆炸半径”上下文

来源：[tirth8205/code-review-graph README](https://github.com/tirth8205/code-review-graph)；趋势证据：[GitHub weekly trending](https://github.com/trending?since=weekly)

**有价值的点。** 该项目本周登上 general/Python 趋势，定位不是通用 RAG，而是用 Tree-sitter 把函数、类、导入、调用与测试关系写入本地 SQLite 图谱；在 review 时沿图计算受影响调用方、依赖和测试，只把最小相关文件集交给 agent。它支持 MCP、CLI、hook/watch、GitHub Action，并显式覆盖 Codex、Claude Code、Copilot 等平台。

**痛点。** 大仓库 review 常见的两个失败模式是：为了保险把大量代码塞进上下文，或只看 diff 而忽略调用链和测试缺口。两者分别导致 token 浪费与漏检。

**方法 / 机制。** 首次构图后增量重解析变动文件；`detect_changes` 输出 blast radius 和风险信息；CI 可发布固定 PR 评论，并可选择把风险阈值变成 merge gate。README 报告六个开源仓库上“全仓语料 vs 图查询”的中位 token 缩减约 82 倍，但也清楚说明 528 倍仅为单个最佳案例；影响范围的 recall 因为部分 ground truth 由同一图产生而是循环上界。

**效果 / 结果。** 最可信的效果是让 review 输入可解释、可复现、可按变更更新，而不是 README 的最大节省数字。对个人最可迁移的做法是：在让 agent 改多模块前，先产出“改动文件 -> 调用方/依赖/测试 -> 需验证命令”的小型影响表；小型单文件改动无需付出构图开销。**待验证：** 项目的 JavaScript/Go flow detection、检索排序和真实历史共变效果仍有限，不能把图谱当作完备架构事实。

### 4. `OpenCodeReview`：确定性规则与 LLM 深审分工

来源：[alibaba/open-code-review README](https://github.com/alibaba/open-code-review)；趋势证据：[GitHub daily trending](https://github.com/trending?since=daily)

**有价值的点。** 本周日榜出现的 Alibaba 开源 CLI 把 diff 读取、代码搜索和 LLM tool-use review 接在一起，同时保留 NPE、线程安全、XSS、SQL 注入等确定性规则。README 称其源自内部代码审查助手，曾服务数万开发者并发现数百万缺陷；这些规模数字是项目自述，不能外推为通用准确率。

**痛点。** 仅靠 LLM 读 diff 容易缺少周边上下文且输出不稳定；仅靠静态规则又难覆盖业务语义、跨文件约束和变更意图。

**方法 / 机制。** `ocr review` 可审工作区、分支范围或单提交，agent 可读取完整文件、搜索仓库和检查其他变更文件后生成行级结构化评论；`ocr scan` 则可在没有有意义 diff 时审查整文件/陌生目录。配置模型后先做连通性检查，支持中断会话恢复。

**效果 / 结果。** 可迁移的模式是“确定性守住已知高风险类，agent 专注上下文与新颖风险”，并把 review 结果绑定到具体行和证据路径。个人可先在本地 diff 上运行 lint/security/test，再让独立 review agent 读取这些结果与变更范围；不要让同一个实现 agent 自评即充当唯一验收者。

## 跨来源的实用模式

1. **把长任务设计成事件流。** 至少记录目标、阶段、工具输出、产生的 diff、验证结果、暂停原因和下一步。这样人可以在审批点接手，agent 也能在新会话中恢复，而不是从聊天摘要猜测状态。
2. **把“上下文最小化”改成可证明的选择。** 不是泛泛要求 agent 少读文件，而是要求它报告为什么这些调用方、依赖和测试与本次变更有关，并保留查询/搜索证据。
3. **将复查与实现分离。** 实现 agent 可追求完成任务；review harness 应有独立输入（diff、规则扫描、影响范围、测试日志）与独立停止条件。确定性检查先行，LLM 处理难以规则化的语义审查。
4. **风险由动作决定。** 阅读、局部可逆编辑、跨目录/网络/凭据/部署等动作应处于不同策略层级；审批要在执行前发生且能在事后审计。

## 给个人 AI 工作流的可执行清单

```text
任务卡（范围 + 成功证据 + 禁止动作）
  -> 只读探索，列出最小相关文件/调用方/测试
  -> 在工作区内实现并保存事件与 diff
  -> lint / targeted test / regression / security 证据
  -> 独立 review（规则结果 + diff + 爆炸半径）
  -> 对外部写入、删除、部署、付费调用人工批准
  -> 保存失败样本与下一次可复用检查项
```

项目层面优先投资两件低成本设施：一是统一的任务事件记录（即使只是每次任务一个 Markdown/JSON 工件）；二是变更影响模板，强制列出受影响模块、测试和证据。二者都比立刻部署复杂多 agent 编排更容易验证收益。

## 推断与待验证

- **推断：** agent 能否持续做长任务，越来越取决于宿主是否能呈现可恢复状态与审批状态，而不只取决于单轮模型能力。
- **推断：** 对中大型仓库，结构化上下文选择会比增大原始上下文窗口更容易审计；但对小改动可能得不偿失。
- **待验证：** `code-review-graph` 的 token/影响分析收益是否在目标项目语言、框架和真实 PR 中成立；先以一周 PR 为样本，比较图谱建议的测试集、人工发现的问题数和构图维护时间。
- **待验证：** `OpenCodeReview` 的规则集和外部模型端点是否满足项目的隐私、许可证与误报容忍度；在任何源码外发前独立审计配置与数据流。
