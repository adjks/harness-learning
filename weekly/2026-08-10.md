# Weekly Harness Notes - 2026-08-10

## 本周结论

本周的新增信号指向同一个分界线：长时运行的 agent 不能只靠“更长的聊天记录”维持质量。可靠性来自可检查的外部状态——明确目标、可测验收、待办归属、人工闸门、证据、配额和可控的记忆装载。本周资料一端给出了八个科学计算项目的真实复盘，另一端则出现了把这些控制面拆成开源组件的趋势项目。对个人而言，最值得先固化的是**每次任务的验收证据与停机条件**，不是先部署一个更复杂的多 agent 系统。

### 1. OpenAI：科学计算案例把 agent 的瓶颈明确为“可测验证”

来源：[Scientific computing in the age of agentic AI](https://openai.com/index/scientific-computing-agentic-ai/)（2026-07-28）。这是本周新纳入的资料，而非对先前 OpenAI harness 文章的重复：它提供了八个实际项目（五个只用 Codex、三个混用 Codex 与 Claude Code）的回顾性案例与失败边界。

**有价值的点。** 报告的共同结论不是“agent 已能替代专家”，而是研究者的角色转向规定要做什么、怎样度量正确，以及何时可以交付。最强的验证不是让 agent 自评，而是把输出与外部参照物比对：精确输出一致性、旧工具的行为等价、统计性质，或预先由模拟数据确定的答案。

**痛点。** agent 能快速写出初版，却不能可靠判断科学有效性，甚至会在明显错误时表现得自信；边界条件和数值细节构成了最耗时的“最后一公里”。低成本重写还可能制造多个相近分叉，反而稀释维护者的注意力。

**方法 / 机制。** 团队把大目标拆为小改动，以中间 benchmark、测试系统和反馈循环逐段推进；在上游维护者存在时尽早协作，若必须分叉则预先指定维护责任和长期计划。报告特别区分了“实现速度”与“验证、归属、维护”三项人类责任。

**效果 / 结果。** 案例贡献者称 agent 显著加快了维护、迁移、优化和新实现，使小团队能承接原本需要更多工程支持的任务；这是回顾性案例而非可泛化的因果评估。可迁移结论是：任务合同应先写出**外部 oracle + 通过阈值 + 维护归属**，再让 agent 实现。

### 2. `LoopX`：将长任务治理压缩为目标、闸门、证据和配额

来源：[huangruiteng/loopx README](https://github.com/huangruiteng/loopx)，趋势证据：[GitHub Python weekly](https://github.com/trending/python?since=weekly)。该仓库本周在 Python weekly 新出现，页面显示本周新增 3,518 stars；这一热度只作为发现线索，以下内容以 README 的机制为准。

**有价值的点。** `LoopX` 不替代 Codex/Claude Code/Cursor 的执行 loop，而是把跨轮次稳定的控制状态放进独立、local-first 的控制面：objective、scope、todos、human gates、evidence、quota、handoff。它把“何时应继续花费一次 agent turn”从计时器判断变为带证据与配额的状态转移。

**痛点。** 多日任务中目标会变、证据会过期、任务会交接；只保存聊天历史或定时唤醒，容易在无有效进展时继续消耗预算，或在需要 owner 决策时含糊地卡住。

**方法 / 机制。** README 的最小循环是：先 `quota should-run`，再 claim 一个 todo，更新 todo 与证据、刷新状态，最后仅在有效 writeback 后计入配额。它要求把“等待 owner”具体化为可回答的问题，并允许经过审计的安全 fallback，但禁止绕过闸门。项目还把危险权限、发布和生产写入明确留给人类。

**效果 / 结果。** 项目展示了跨 200+ 小时墙钟时间的公开贡献/实验案例，但 README 已明确这不代表持续模型运行、无人生产自治或独立复现；应当按 showcase 的证据强度审阅。个人不必引入完整控制面，也可迁移其最小模式：每个自动化运行只记录“本轮证据、下个 todo、是否需要人、是否允许再跑”。

### 3. `TencentDB-Agent-Memory`：把记忆当作有版本和权限的资产，而不是全局提示词

来源：[TencentCloud/TencentDB-Agent-Memory README](https://github.com/TencentCloud/TencentDB-Agent-Memory)，趋势证据：[GitHub weekly](https://github.com/trending?since=weekly) 与 [TypeScript weekly](https://github.com/trending/typescript?since=weekly)。本周该项目在 general/TypeScript weekly 出现，README 标注 Team Memory Beta 正快速演进。

**有价值的点。** 仓库将可复用信息分为 Chat Memory、Skill、Wiki 和 CodeGraph，并为每项资产记录版本、来源、所有者、可见性、绑定 agent 和使用状态。核心想法是让下一位 agent 继承经过筛选的“存档”，而不是重读所有聊天和仓库。

**痛点。** 会话复用常走向两个极端：每次从零解释项目，或把所有历史塞回上下文。前者重复劳动，后者造成噪声、上下文膨胀与隐私外泄；普通 RAG 也回答不了“哪一版仍有效、谁能用、该给哪个角色”。

**方法 / 机制。** 对话从原始 L0 逐步蒸馏为事实/约束（L1）、场景知识（L2）和长期模式（L3），检索会从较高层快速启动，在需要精确事实时回落到 L1/L0，并以数量、字符预算和超时限制避免记忆压垮上下文。Skill 默认私有，须 review 后共享；`private`、`team`、`restricted` 与 agent 定向装载把知识复用和最小授权结合起来。代码图只给实现和审查角色，减少无关上下文。

**效果 / 结果。** 作者主张资产化记忆能减少 turns、重复劳动并提高稳定性；目前是快速演进的 Beta，公开页面未给出独立的生产对照指标，故不应把收益当成保证。可迁移做法是为个人项目维护小型、可复核的三类资产：当前约束、已验证命令、决策/失败记录；默认按任务加载，而非永久注入所有 agent。

### 4. `agent-skills`：把“规范—计划—构建—验证—评审—交付”做成可安装的生命周期接口

来源：[addyosmani/agent-skills README](https://github.com/addyosmani/agent-skills)，趋势证据：[GitHub daily](https://github.com/trending?since=daily)。该项目本周出现在 general daily；README 提供面向 Codex、Claude Code、Cursor、Copilot 等的安装路径。

**有价值的点。** 它把高级工程师常用的流程、质量门和反合理化检查打包成 skills，而非把技巧散落在长 prompt 里。命令按生命周期映射为 `/spec`、`/plan`、`/build`、`/test`、`/review`、`/ship`，把“何时需要何种约束”变成显式入口。

**痛点。** 通用系统提示词难以在每次任务中稳定地触发规格、测试、审查和交付边界；全自动执行又容易把人从高风险决策中移除。

**方法 / 机制。** `/build auto` 的设计很有代表性：用户只在计划阶段批准一次，后续逐个任务自动执行、测试驱动并独立提交；失败或风险步骤暂停。仓库同时承认便携性缺口：只安装单个 skill 时，仓库级参考清单不会一并复制，可能弱化技能效果，因此建议全仓整合或把所需 reference 随 skill 一起带上。

**效果 / 结果。** 该方法的主要收益是流程一致性和更少的手动编排，并非证明某个 skill 必然提高正确率。对个人来说，应先把真正高频且可验收的任务（例如 bug 定位、PR review、发布前检查）做成窄 skill；每个 skill 必须声明触发边界、可运行的验证和停机/升级条件。

## 跨来源实践模式

1. **把“成功”改写成外部可观测命题。** 先列基线、oracle 或 CI/测试命令，再允许 agent 写实现；没有可测信号时，产物只能标记为探索性草案。
2. **对长任务维护轻量控制状态。** 一张 `objective → next todo → evidence → gate → budget` 状态卡，通常比继续扩大聊天记录更能避免漂移和无效循环。
3. **记忆按资产与角色分发。** 把原始日志留作追溯，把短小、版本化的约束/流程/代码影响信息按需提供给执行者和审查者；默认私有、显式共享。
4. **自动化要有可见的停止语义。** 失败、证据未更新、预算耗尽、越权或需要产品判断时应暂停并提出具体问题；不要把“定时再次运行”当成进展。
5. **技能的价值在闭环，不在数量。** 一个好的 skill 既限定何时适用，也写清输入、产出、验证、风险升级与引用资料；缺少 reference 的可移植安装应被视为降级运行。

## 对个人 AI 工作流的建议

- 对超过一小时或会跨会话的任务，先创建一页任务状态：目标、允许范围、外部验收、当前 todo、最近证据、下一次允许运行的条件。
- 让实施 agent 与 reviewer 使用不同的最小上下文包：实施者获得范围和验收，reviewer 获得变更、证据、风险清单与必要的调用影响；避免二者都吃完整历史。
- 每次自动化先检查“是否有新的证据或新的可执行 todo”；没有则安静退出，而不是生成重复总结或继续调用模型。
- 只有在重复、边界稳定且已有验证命令的任务上自动串联 spec/plan/build/test；外部写入、发布、费用和维护归属仍设置人工闸门。

## 对项目的含义

本知识库后续可用统一字段记录每个案例：`来源可信度 / 任务类型 / 外部验证 / 状态与交接 / 权限边界 / 维护归属 / 证据强度`。这能避免把工具宣传、趋势热度和可复现工程结果混为一谈，并使后续周报能追踪“已有来源本周新增了什么”。

## 推断与待验证

- **推断：** 对个人和小团队，先做外部验证与状态卡，通常比先搭多 agent 编排更能降低返工；这来自多来源的机制一致性，尚不是受控实验结论。
- **待验证：** `LoopX` 的公开案例应按其展示的证据分级逐一复现；不能从“200+ 小时 elapsed”推导无人值守的实际模型运行时长或成功率。
- **待验证：** TencentDB Agent Memory 的分层记忆、访问控制和上下文预算设计合理，但公开 README 尚未给出独立、可复现的效率/准确率对照。
- **待验证：** skills 生命周期接口是否减少缺陷，取决于各个 skill 的具体内容、参考资料是否随安装迁移，以及执行环境能否实际运行验证。
