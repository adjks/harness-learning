# Weekly Harness Notes - 2026-10-19

## 本周结论

本周的增量不在于让 agent 有更多权限，而在于把一次自动化执行收束为一条**能被重放、验证、审计且不过度采集内容的证据链**：GitHub 的 agentic autofix 必须重跑 CodeQL 后才创建 draft PR；管理策略可要求客户端启动前获取新鲜配置、否则 fail closed；遥测可按字段最小化启用；Anthropic 的 Code Review 则把自动 review 的速度、深度和实际使用反馈公开为可选择的服务级别。新发现的 `october-harness` 展示了另一端：多 agent 的工作消息、认领和确认需要是 durable protocol，而不只是 prompt 中的一段分工描述。

## 本周新增资料

### 1. GitHub Copilot：Agentic autofix GA，将安全修复闭环限制在独立扫描器的 verdict 内

来源：[Agentic autofix for code scanning alerts general availability](https://github.blog/changelog/2026-10-15-agentic-autofix-for-code-scanning-alerts-general-availability/)（2026-10-15）。这是本周新增的 GA 更新，不是此前已记录的 Copilot Memory、local sandbox 或 secret classifier 的重复。

- **有价值的点**：从 code-scanning alert 出发，agent 不是只生成 patch：它跨文件探索、提出修复、重跑 CodeQL、必要时迭代，再创建给人审阅的 draft PR。PR 还带上为何能关闭 alert 以及实际做过哪些验证的摘要；这把“模型说已修好”替换为独立 scanner 的可见判定。
- **痛点**：安全修复常存在局部修改掩盖跨文件调用链的风险；只依赖自然语言 code review，既难判断 alert 是否真正消失，也难留存可复查的验收证据。批量处理又容易把修复范围扩大到人无法逐项审查的程度。
- **方法 / 机制**：在默认分支的 alert 上把 Copilot 设为 assignee；可在列表或 campaign 中一次选择最多 25 个 alert，但输出是一份待审 draft PR。控制面先要求企业管理员启用 Advanced Security 的专用 policy，组织/仓库管理员再开启；成本面同时消耗 AI Credits 和 Actions minutes，并可按 SKU 设预算。
- **效果 / 结果**：GitHub 明确承诺的是 CodeQL 被再次运行、alert 关闭前才进入 PR 审阅阶段，并非“所有安全问题已修复”。其对 only-default-branch 的限制也意味着 PR/非默认分支 alert 尚不能走该链路；批量 25 项是否导致 review 质量下降，需要团队自行以关闭率、回滚率、review 时长和误修率验证。

### 2. GitHub Copilot：治理策略的关键属性是 freshness，缓存不可确认时应 fail closed

来源：[Enterprise managed settings enforcement updates](https://github.blog/changelog/2026-10-13-enterprise-managed-settings-enforcement-updates/)（2026-10-13）。本周的新信息是 **policy freshness 与 client-version 也成为 agent sandbox 的执行前置条件**，而不是对 2026-10-07 local sandbox GA 的重复报道。

- **有价值的点**：`forceRemoteSettingsRefresh=true` 可令 Copilot CLI、VS Code 和 Copilot app 在启动时拉取当前托管策略；若无法确认，客户端不使用缓存策略继续工作，而是 fail closed。`sandbox` policy 还开始强制最低客户端版本，避免团队以旧客户端绕过新控制。
- **痛点**：管理面即使已变更，离线客户端或启动缓存仍可能按旧权限运行。单纯记录“已配置 sandbox”不能回答本次执行实际拿到的是哪一版策略。
- **方法 / 机制**：该开关可通过 server-managed、MDM 或文件配置下发。MDM/文件方式甚至能在首次登录前就要求新鲜配置；server-managed 值在客户端先收到一次后，从后续启动开始要求刷新。正常模式则保留缓存，以获得更快启动和应对短暂服务故障。
- **效果 / 结果**：公告给出了明确的安全语义（无法确认即不运行），但未给出刷新造成的启动延迟、离线失败率或策略漂移事件减少量。对个人工作流而言，适合将“高风险任务必须有新鲜 policy”与“普通本地只读任务可用缓存”分级，而不应无条件要求每次联网。

### 3. GitHub Copilot：可用遥测不等于应采集 prompt 和工具内容

来源：[Client telemetry user attribution and configurable capture](https://github.blog/changelog/2026-10-12-client-telemetry-user-attribution-and-configurable-capture/)（2026-10-12）。该更新与前周已收录的 OTel 发布有关；**本次新增信息**是 identity 与五类内容字段均可独立、默认关闭地治理。

- **有价值的点**：管理员可只采集 `user.name`、本地 OS 用户和主机名来做运行归属，而不采集 prompts、responses 或 tool content。prompt、response、tool arguments、tool output、policy detail 五类内容也可分别启用，显式 managed 值优先于本地、SDK 和环境变量。
- **痛点**：没有身份归属的 trace 难调查异常；但一次性开启完整 prompt/command/output 采集可能把源码、密钥、客户数据、路径甚至 sandbox policy 暴露给观测后端。可观测性与最小化披露不能靠一个笼统的“telemetry on/off”解决。
- **方法 / 机制**：以 `telemetry.capture.identity` 和五个 capture class 配置采集面，全部默认 off；旧 `captureContent` 只是内容类快捷写法，不能开启 identity。GitHub 特别提醒内容类可能包含源码、文件内容、命令、工具输出与路径，且应只发往获批准的 endpoint。
- **效果 / 结果**：该机制改善的是可配置性与优先级可预测性，公告未公布采集对 incident 调查或隐私风险的量化结果。可迁移的原则是：将 run id、任务/用户归属、最终 verdict 作为低敏必需证据；只有针对明确事故才临时提升到命令或 output capture，并限定保留期和接收端。

### 4. Anthropic Claude Code：Code Review GA 用速度、风险深度和真实 PR 使用校准自动审阅

来源：[Code Review is now generally available](https://claude.com/resources/articles/code-review-is-now-generally-available)（2026-10-15）。这是新发布的 Claude Code 团队实践资料，不与先前 AI-Native SDLC、Auto mode 或 startup guide 重复。

- **有价值的点**：GA 前的设计信号是“自动 review 要更安静、随变更规模调整、且更快”，而不只是增加发现数量。管理员可逐 repo 选 Quick、Standard（默认）或 Deep；新 PR 自动触发 review，保留人对最终合入的判断。
- **痛点**：agent 增加提交速度却没有消除 review 瓶颈；若每个 PR 都用同样重的推理，普通修改会等太久且噪声升高，关键路径又得不到更深检查。
- **方法 / 机制**：组织管理员在 Claude Code settings 开启服务、安装 GitHub App 并选择仓库；之后新 PR 自动进入该 reviewer。Anthropic 表示他们自己也将其运行在 PR 上，并用内部观察定位 review 延迟点。报告把 findings 约束为说明问题、触发条件与修复方向的短结论。
- **效果 / 结果**：官方称多数 review 从约 20 分钟降至 6--10 分钟（约 3 倍），且 preview 用户反馈能在人审前发现真实问题。它没有披露 precision/recall、漏报或合入后 defect 指标，因此这个速度/反馈只能视为供应商和用户报告；团队应按仓库风险建立 Quick/Standard/Deep 的抽样复核和 bug-escape 指标。

### 5. 新近发布仓库 `october-dev/october-harness`：协作需有 durable inbox、任务认领与结算确认

来源：[october-dev/october-harness](https://github.com/october-dev/october-harness)（本周检查 README；最新 release `october-v0.87.1-october.5` 发布于 2026-10-11）。本周 GitHub general daily/weekly 与 Python、TypeScript、Jupyter Notebook weekly 趋势入口均已检查；此仓库作为近期活跃、README 可核验的新增 harness 资料纳入，而非根据 star 数字入选。

- **有价值的点**：它把 multi-agent 协作定义成消息协议：agent 发现 peer、发送带 correlation 的 request、worker `claim_task`、回 response、再 acknowledge。消息和 task 是 durable state，公共 Bus 可唤醒空闲 RPC/TUI session；这比“主 agent 记得自己派了什么活”更容易在中断后恢复。
- **痛点**：多个 agent 若只靠临时对话或一个 orchestrator 的上下文协调，容易重复执行、漏收结果、分不清处理完成与仅已看到消息；持续运行的 worker 也会因无新任务而浪费资源。
- **方法 / 机制**：仓库同时提供 terminal、one-shot、JSON、RPC 与嵌入 SDK 形态；Bus 接入需要 launcher address、MCP URL、agent/execution id 与 token，缺少有效配置时不注册 Bus tools/hooks。README 的本地双 worker 示例以隔离 Bus、真实 SDK worker、discovery、task completion、correlated reply 与 acknowledgement 为验收，并在结束后清理。
- **效果 / 结果**：能确认的是协议和可运行示例存在，不能从 README 推出它比其他 harness 有更高完成率或更低成本。特别要注意其表列默认 permission 为 `bypass`，并明确这不是 OS sandbox；采用时应把 durable coordination 与最小权限/隔离分开实施，先把权限改为 ask 或受限模式。

## 跨来源实践模式

1. **闭环的完成条件应由独立系统给出**：安全修复以 scanner 重跑、alert 关闭和 PR evidence 为止；代码 review 的“完成”应包括可解释 finding 与人的 merge decision，而不是 agent 已经输出文字。
2. **策略需要版本与新鲜度语义**：在运行记录中写下 policy id/version、是否刚刷新、客户端版本与是否 fail-closed。否则“被治理过”的说法无法复查。
3. **遥测分层，证据最小化**：默认先保留任务 id、时间、工具种类、权限判定、验证 verdict；收集 prompt、代码和原始输出应当是短期、获批准、可删除的升级措施。
4. **协作协议与权限模型必须两层设计**：durable message、claim 和 ack 能解决恢复/去重；它们不能自动提供 sandbox 或最小权限。运行时应同时验收“谁领取了工作”和“它能访问什么”。

## 对个人 AI 工作流的建议

- 为每个 agent 修改建立可机器检查的 accept gate：例如目标测试/扫描器、退出码、产物路径、通过/失败 verdict；由独立命令而非 agent 总结写入 `evidence/`。
- 给高风险执行设 `policy freshness`：在启动前读取并记录权限配置和工具 allowlist 的 hash；若无法获得必须的本地/远程配置，停止需要写入或联网的任务，而不是静默降级。
- 将观测分成常态与事故两档。常态只写 metadata 和 verdict；事故调试才短期启用输入/命令/output，预先定义脱敏、存储端、保留期和删除责任人。
- 多 agent 任务至少维护 `tasks.jsonl` 或 issue/队列表，含 `task_id`、owner、claim time、correlation id、result artifact、ack 和 stop reason。worker 重启时先恢复未 ack 的项，再创建新任务。

## 对项目的含义

本仓库现在可把“verification、policy、observability、coordination”关联为同一条 run record：`intent → policy freshness → scoped capability → durable task/message → independent verdict → minimal audit record`。后续资料索引应继续区分“运行机制存在”“供应商报告效果”“独立评测确认”三种证据等级；尤其避免因为有 trace 或 dashboard 就误以为已经具备可审计治理。

## 推断与待验证

- **推断**：对代码扫描 alert，先以单 alert 输出一份 PR 会比一次合并 25 个 alert 更利于人类发现错误分类与副作用；但真正的阈值取决于代码耦合度和 reviewer 容量。
- **待验证**：强制 remote policy refresh 在离线开发、高延迟网络和服务故障期间的可用性代价。应测量启动失败/等待时间，并设定风险分级的 fallback。
- **待验证**：Claude Code 的 6--10 分钟与“发现更多关键 bug”是否能在不同语言、repo 尺度与深度级别复现；需采集抽样人工标注的 precision、回归 defect 和 review 负荷。
- **待验证**：`october-harness` 的 durable Bus 语义在网络分区、重复投递、worker 崩溃和 token 轮换时的恰好一次/至少一次边界；README 示例证明基本协议，不等于生产可靠性证明。
