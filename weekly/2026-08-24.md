# Weekly Harness Notes - 2026-08-24

## 本周结论

本周最清楚的新变化不是又多了一种 agent，而是 **把可复用能力、触发入口、权限边界和验收器分别做成可治理的对象**。GitHub 将 skills 与 MCP server 打包为跨客户端插件，同时把 MCP 允许/拒绝策略下沉到托管配置；评论触发的 Copilot automation 则把“请求 agent 做一件事”变成可审查的 repository 事件。Aria 的实验提供了一个更强的反例：agent 不必被限制为固定的推理策略，只要在独立、不可绕过的 verifier 反馈下反复修订。`thecarbonlayer/carbon` 则用一个可运行的教学仓库，把这些概念落实为可替换、可 fake、可分别验收的 harness 原语。

对个人工作流，优先级应是：把高频能力封装成小型、版本化包；以 issue/PR 评论或任务状态作为明确触发；为外部工具设 allowlist；将“完成”绑定到独立 oracle，而不是 agent 自述。多 agent 或自动改进应建立在这些边界稳定之后。

### 1. Agent Plugins 1.0 与 MCP allowlists：把能力包和准入策略分开治理

来源：[Agent Plugins 1.0 in VS Code, Copilot CLI, and the Copilot app](https://github.blog/changelog/2026-08-12-agent-plugins-1-0-in-vs-code-copilot-cli-and-the-copilot-app/)，[MCP allowlists in enterprise managed settings](https://github.blog/changelog/2026-08-06-mcp-allowlists-in-enterprise-managed-settings/)。两项均为 2026-08 新发布的 GitHub Copilot 能力；不是对既有 skills 或 MCP 一般概念的重复。

**有价值的点。** Agent Plugins 1.0 把 skill、MCP 配置和客户端特有扩展放进一个可跨兼容客户端发现的包：共用内容置于 `skills/` 与 `mcp.json`，特定客户端内容置于命名空间目录。与此同时，MCP allowlist 以远端 URL、本地命令（含参数）或名称匹配 server，并可在企业与团队层叠加。这把“要给 agent 什么能力”和“哪些能力可以在此环境运行”拆成两个独立版本面。

**痛点。** 同一流程若要支持多种 coding agent，通常需重复维护多份目录、manifest 与安装说明；而一旦插件含 MCP，方便分发也可能让未经审查的外部工具扩散。只根据 user 可改的显示名称授权又容易被规避。

**方法 / 机制。** 插件标准保留可移植的 skills/MCP 部分，同时把 Copilot 特性隔离在 `com.github.copilot/`；托管设置以 `enabledPlugins`、已知 marketplace 与严格 marketplace 控制安装范围。MCP 策略使用 `allowedMcpServers` 和 `deniedMcpServers`；URL 会 canonicalize 以降低规避风险，本地命令需精确匹配；配置无法验证时 fail closed，且多层策略要求同时通过。

**效果 / 结果。** 兼容客户端可以复用一份能力包，管理者不必为每个客户端另建一套准入政策。公开资料说明该标准已在 VS Code、Copilot CLI、Copilot SDK 与 Copilot app 支持，而 allowlist 在 app、CLI、VS Code 强制执行。可迁移结论不是马上引入企业管理系统，而是：把个人的插件清单与允许调用的 MCP/命令清单分别写入版本控制；MCP 的 `name` 仅适合作为提示，不适合作为安全决策。

### 2. GitHub Copilot 评论触发 automation：把异步 agent 入口变成可审计的事件

来源：[Trigger Copilot automations with comments](https://github.blog/changelog/2026-08-03-trigger-copilot-automations-with-comments/)。

**有价值的点。** GitHub 允许 issue 或 pull request 评论中的指定文字触发 cloud agent automation。入口不再是某人在聊天窗口里临时复制一段请求，而是关联到具体 issue/PR 的、可见且可回溯的事件；官方给出的模式包括补文档、调查错误日志、为技术债建立 follow-up issue。

**痛点。** 定时 agent 容易在不相关时间运行，手工委派又会丢失触发原因、范围和回写位置。将 agent 任务绑定到缺少上下文的自由文本，还会使 review、重试和权限判断混在同一轮会话中。

**方法 / 机制。** 在 repository 的 Agents → Automations 中配置评论触发文字；触发事件天然携带 issue/PR 上的讨论与链接上下文。将触发短语设计成窄的任务类型，例如 `@copilot investigate-log`、`@copilot draft-docs`，并要求 automation 只回写分析、补丁或 follow-up，不自行合并/发布；高风险动作仍在 CI、分支保护或人工 review 后进行。

**效果 / 结果。** 这为“人提出意图 → agent 异步执行 → 代码审查/CI 决定接受”提供了明确控制点，尤其适合重复但不应无人值守的维护工作。功能可用性受 Copilot 计划及组织的 cloud-agent policy 约束。**待验证：** 评论本身可能包含不可信文本；对外部贡献或宽泛触发语，应先在受限仓库和只读/低权限任务中演练，不能把评论触发误解为天然安全。

### 3. Aria：让独立 verifier 约束开放式 code agent，而非把策略写死

来源：[Harnessing Code Agents for Automatic Software Verification](https://arxiv.org/abs/2607.06341)。

**有价值的点。** 论文的反直觉结果是：面对 Coq 证明，不必把 agent 限制在人工设计的 premise selection、tactic prediction 或 divide-and-conquer 策略中。将整条 lemma 交给通用 coding agent，再以 proof-kernel 为不可绕过的验收器，反而能获得更高覆盖。

**痛点。** 把领域专家策略固化进 harness 会造成维护负担，并可能排除模型本可发现的替代路径；而让 agent 自由编辑又会把“看上去像证明完成”错当正确，或陷入无终止重试。

**方法 / 机制。** Aria 通过 `claude -p` 的非交互调用运行 agent；Coq kernel 只在 proof 闭合时接受结果。失败时 harness 返回失败步骤和未解决目标，agent 最多重试 30 次。论文还描述了声明式 Harness Hook Language，以通用 code-agent interface 对接 Claude Code 与 Codex；约束在 verifier 与薄策略层，而不是强行规定每一步推理。

**效果 / 结果。** 作者报告在 Iris 四个核心模块中自动证明 4,257 条 lemma，并完成 217 条 Rust 标准库验证 lemma；在 reglang 完成 318 条，在 Iris 的 Lean 4 port 完成 72 条未移植 lemma。它是研究论文的特定领域实验，不等同于一般软件测试的成功率。对个人最可迁移的是：凡有可执行 oracle 的任务，允许 agent 探索实现空间，但将“接受、覆盖与终止”交给独立工具；例如编译器、类型检查器、契约测试、快照比较或生产只读查询结果。

### 4. `thecarbonlayer/carbon`：逐原语建造 harness，并把“测试通过”与“真实 agent 可用”分成两道门

来源：[thecarbonlayer/carbon README](https://github.com/thecarbonlayer/carbon)。该项目为新发现的开源资料，README 公开其 15 个按 commit/tag 组织的章节与验证机制；本周并非将其热度当作结论。

**有价值的点。** 仓库按 15 个原语逐步实现 provider、历史、指令、上下文、工具/审批、context compaction、skills、sandbox、耐久记忆、orchestration、subagent、verification、observability 和 UI。它的关键教学价值不是“功能清单”，而是每个外部接缝都可用 fake 替代：模型、sandbox、trace exporter 都可离线测试。

**痛点。** 很多 harness 在单一 agent loop、UI、provider 和工具代码中混在一起，导致无法离线复现、无法知道策略还是基础设施造成失败，也无法安全尝试自动优化。单纯单元测试通过，也不代表真实模型和工具链能完成能力闭环。

**方法 / 机制。** 核心依赖单向：`ui/ → harness/ → model/`；每章都有行为测试。`uv run verify` 运行 format/lint、mypy、pytest 和 smoke import，作为离线确定性底线；`uv run accept ch-NN` 则用真实模型端到端断言该章节能力。项目将自改配置限制在已审核的策略菜单，借由 `surface_manifest()` 声明不可变边界，禁止其放宽 verification 或 workspace 限制。

**效果 / 结果。** 这使“离线可验证的实现正确”与“真实 agent 可用”成为两项不同主张，并让学习/评审者能回到特定 tag 查看一个原语刚引入时的最小改动。个人无需重写 agent 框架，但可直接采用两道门：先运行无网络、可重复的测试/静态检查，再在受控样本上运行一次真实工具验收；自动调整 prompt、压缩或工具策略前，先固定不可调的安全与验收边界。

## 跨来源实践模式

1. **能力、入口、权限、验收应有独立所有者。** Plugin/skill 决定能做什么；评论/issue 决定为何与何时做；allowlist/sandbox 决定能碰什么；oracle/CI 决定能否接受。把四者混在一段 prompt 中，任何一项变更都难以审查。
2. **以事件驱动替代模糊的后台“持续运行”。** 评论触发、任务状态与明确回写使一次 automation 有起点、上下文和审查对象；触发不应自动授权合并、部署或外部写入。
3. **开放式生成需要硬性反馈，不一定需要细粒度剧本。** Aria 说明可将创造性的搜索留给 agent，同时让不可伪造的 verifier 决定通过、失败信息与停止上限。
4. **两种验证回答两种问题。** 离线/确定性 gate 验证 harness 本身没有回归；真实模型/工具 acceptance 验证工作流可实际完成。只有前者会遗漏集成问题，只有后者会使失败难以定位且成本不稳定。
5. **可移植不等于可无条件安装。** 跨客户端标准降低复用成本，也扩大供给链和 MCP 工具面；版本化 allowlist、最小权限、固定 marketplace/来源和人工批准仍是必要配套。

## 对个人 AI 工作流的建议

- 把一个常用流程拆成四个小文件或字段：`能力包（skill/脚本）`、`触发条件`、`允许的工具/命令`、`验收命令与人工终态`。先能独立审查，再考虑自动触发。
- 对 issue/PR 评论自动化采用“创建草稿 / 给出调查报告 / 创建后续任务”的低风险输出；合并、发布、修改密钥与生产写入必须留在独立人工闸门之后。
- 为每类任务选一个独立 oracle，并明确 retry budget：例如“最多 3 次；每次失败必须保存测试/日志摘要；oracle 不通过则 `Needs Review`”。不要让 agent 用改测试、删断言或口头总结取得“通过”。
- 将验证分成快速离线 gate 与少量真实 acceptance sample；记录二者结果、耗时、输入版本和允许的工具集合。这样才能判断某次流程优化是真提升，还是恰好遇到容易的任务。
- 共享 skills/MCP 前审查其网络、文件和凭据边界；个人也可维护一个小型 allowlist，而不是把“装上能用”误当可信。

## 对项目的含义

后续知识库可把“能力包”和“治理包”分开索引：前者记录 skills、工具、复用范围与版本；后者记录触发器、权限边界、oracle、retry/stop policy 和人工终态。这样能将可迁移的工作流从某一厂商界面中抽离出来，也能更准确地区分工具方便性、实际验证证据与安全控制。

## 推断与待验证

- **推断：** 对个人开发，先把一个单 agent 工作流拆成 capability / trigger / policy / oracle 四块，比先增加 agent 数量更容易定位返工与越权来源；此判断来自本周机制的共同结构，尚无个人开发者受控比较。
- **待验证：** Agent Plugins 1.0 的跨客户端可移植性仍取决于各客户端对 skills、MCP 和命名空间扩展的实际支持范围；安装前应做最小 smoke test，而不是仅检查 manifest。
- **待验证：** MCP allowlist 的 URL/命令匹配能控制已知 server 身份，但不能替代对 server 内容、依赖、提示注入防护与数据外发的审计。
- **待验证：** Aria 的高覆盖结论来自形式证明的强 oracle 和特定 benchmark；普通业务需求通常没有同等强度的 kernel，需先投资构造更接近外部事实的验收器。
- **待验证：** `carbon` 的真实 acceptance gate 会引入模型版本、网络和成本波动；个人应将它用作小样本验收，而不是把每次 CI 都变成昂贵的在线 agent run。
