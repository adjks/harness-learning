## 本周结论

### 1. OpenAI Agents API：把长运行能力拆为上下文、工具、并行和环境四个可替换层

来源：[Introducing the Agents API](https://openai.com/index/introducing-the-agents-api/)（2026-09-10）及其 [开发者概览](https://developers.openai.com/api/docs/guides/agents)。

- **有价值的点**：API 将 Codex 的运行时能力作为托管控制面暴露，但不强迫采用某个执行环境。调用方可保留自己的 VPC、文件/密钥存储和业务工具，同时选择托管 sandbox、自管基础设施或合作方环境；这避免把“agent 编排”与“生产系统访问权”混成一个不可拆的产品选择。
- **痛点**：长任务会耗尽上下文，工具目录大时每轮都塞入 schema 会挤占有效上下文，多步任务自行 fan-out 又容易让调用方重复造 session、队列、结果收集和恢复机制。
- **方法/机制**：会话接近窗口上限时自动 compact 早期上下文；tool search 按需加载定义以维持缓存并减少 token；programmatic tool calling 在代码中并行、串联及过滤结果；子 agent 各有独立上下文、主 agent 汇总。环境层可挂载 skills/plugins/capability directories，任务产物明确写入输出目录，而不是仅留在聊天记录中。
- **效果/结果**：厂商客户引述包括 Ciridae eval 0.71→0.85 与 4× latency reduction、SafetyKit 单 case 成本降 60%、Hypha 失败响应降 86%。这些是供应商/客户自述，**待验证**，不可当作通用基准；但“工具按需发现 + 子任务隔离上下文 + 文件化产物”是个人 harness 可测量复刻的机制。

### 2. OpenAI《Research acceleration》：并发产能先暴露系统瓶颈，仍须保留人的停止权

来源：[Research acceleration: The view inside OpenAI](https://openai.com/index/research-acceleration-view-inside-openai/)（2026-09-06）。

- **有价值的点**：文章公布的不是单次 demo，而是组织层的使用快照：到 8 月中，研究组织每一人类工作日使用约 3.1 agent-workdays，且运行 4 个以上并发 agent 的研究者比例上升。它同时明确人仍决定研究优先级、判断结果、以及 scale/pause/deploy。
- **痛点**：把写代码提速误认成端到端研究提速，会忽略实验基础设施、评测、训练安全与结果判读中的串行约束；高难任务还会因为缺少人类 steering 而失败。
- **方法/机制**：把可定义、可落地的任务交给并发 agent；将成功按能找到 ground-truth outcome 的任务分桶衡量，而非只收集主观满意度；当安全风险不足以防护时暂停或收紧具体工作负载。文中也记录到多个基础设施 office hours 的需求下降，说明 agent 先承担了常见排障。
- **效果/结果**：从 1–7 月、可找到真值的任务中，多个难度桶的成功率上升，较高层级和更长时程的委派变多；作者明确称测量仍是 preliminary，复杂任务依旧需要大量人类 steering。可迁移结论不是“开更多 agent”，而是给每类并发任务设置真值、所有者和可暂停的资源预算。

### 3. GitHub Copilot：策略必须可证明已生效，并且组织级限制不能被本地“方便”覆盖

来源：[Enterprise managed permissions for GitHub Copilot agent operations](https://github.blog/changelog/2026-09-09-enterprise-managed-permissions-for-github-copilot-agent-operations/)（2026-09-09）和 [Enterprise-managed sandbox in Copilot for JetBrains](https://github.blog/changelog/2026-09-08-enterprise-managed-sandbox-in-copilot-for-jetbrains/)（2026-09-08）。

- **有价值的点**：前者把 shell、文件读写和网络域名分为 block / require approval / allow，且企业策略不能被用户、工作区、自动批准或历史批准弱化；后者把 sandbox、filesystem/network、proxy、开发工具和 Keychain 访问纳入集中策略，并提供 policy diagnostics。两者共同补上了“有 policy”与“设备实际执行了 policy”之间的缺口。
- **痛点**：只有 prompt 或项目配置时，使用者可以为了减少弹窗而扩大权限；只有中心化配置但没有诊断时，管理员也难以判断客户端是否收到并执行了限制。IDE 与终端上下文互通还会意外扩大 agent 看见的选择、环境变量和文件范围。
- **方法/机制**：策略优先级高于 local/session convenience；在 IDE 中锁定受管控项并显式标识；诊断页面验证策略检测/执行。JetBrains 版还让 CLI 用 `/ide` 引入当前选择、diagnostics 与文件引用，并提示 shell 可继承 IDE terminal 环境、Python interpreter，因此上下文连接应与权限策略一并审查。
- **效果/结果**：功能提供方未披露缺陷率或泄漏率下降，且 JetBrains sandbox policy 仍为 public preview，故结果**待验证**。但对个人项目可以立即采用等价最小版：将 `deny` 置于任何可编辑的 allowlist 之上，并把每次任务启动时的“effective policy + 可访问路径 + network 状态”写入 dry-run 报告。

### 4. GitHub Trending `openai/plugins`：以插件为最小可分发单元，避免“复制一段神奇提示词”

来源：[openai/plugins](https://github.com/openai/plugins)（本周 GitHub Trending general weekly/Python weekly；仓库 README 于本周检查）。

- **有价值的点**：OpenAI 的新推荐路径从单独 skills 仓库转为插件集合；每个插件以必需的 `.codex-plugin/plugin.json` 作为稳定入口，可按需要组合 skills、MCP、agents、commands、hooks、assets 与 app 配置。`openai/skills` README 也明确标记为 deprecated，并指向此仓库与 Build plugins 指南。
- **痛点**：团队把规则、工具配置、hook 和素材散落在文档或个人目录后，安装、升级、审计和按项目选择都会变得不可重复；一个“万能 agent 配置”又会把无关权限和上下文带进所有任务。
- **方法/机制**：以 manifest 标识能力包，用 marketplace 列出可发现的插件，按领域提供完整样例（Figma、Notion、iOS/macOS、Web、Expo、Netlify、Remotion、Google Slides）。核心不是把所有东西装上，而是让每项可运行能力有可检查的声明边界和依赖。
- **效果/结果**：这是示例集合，并没有给出可靠的生产提效数值。**推断**：将项目惯例封装为版本化插件，会降低新成员/新机器复现成本；应通过安装后可用能力、hook 触发率、失败回滚率来验证，而非仅看安装数量。

### 5. GitHub Trending `github/spec-kit`：让实现循环对 specification 收敛，而不是只对“代码写完”收敛

来源：[github/spec-kit](https://github.com/github/spec-kit)（本周 GitHub Trending general weekly/Python weekly；README 标注近期 1.0.0 里程碑）。

- **有价值的点**：仓库把可执行 specification 放在代码之前，并把 agent workflow 固化为 constitution → specify → plan → tasks → implement → converge。最后一步要求反复实现与校验，直到相对 spec、plan、tasks 都报告 Converged，直接对应 agent 容易“功能看似完成、约束已丢失”的问题。
- **痛点**：长提示词不能持续承载产品原则、边界和验收；只跑 test 也可能遗漏需求、非功能约束和计划偏离。并发 agent 会放大这种“局部测试绿、整体意图漂移”。
- **方法/机制**：先以 constitution 建立项目原则，再把需求、计划和可执行任务分别外化；支持不同 coding-agent integration，并允许 extension/preset 调整流程。该仓库把 1.0.0 的含义描述为适应性而非冻结，适合 agent 时代不断校准流程模板。
- **效果/结果**：项目未提供可比较的缺陷率或周期缩短实验，因而“SDD 必然更快/更可靠”是**待验证**。可靠可迁移的部分是把 `converge` 变成独立 gate：用需求追踪、diff 范围和验收命令共同判定完成，而不是让实现 agent 自己宣布结束。

## 跨来源实践模式

1. **连续性不等于无限上下文。** 状态应包括 compact 后保留的决策、文件产物和可恢复 session；工具细节及大结果按需加载或在代码内过滤。
2. **并发需要一个资源与真值控制面。** 每个子任务须有目标、最大并发/预算、独立上下文、可验证输出和明确 owner；人保留暂停、改优先级和接受最终结果的权力。
3. **有效策略必须比配置更强。** 能够读取、编辑、执行和联网的规则独立建模；高优先级 deny 不可由 session 自动批准绕过；每次运行能导出实际生效的策略证据。
4. **把流程知识做成选择性安装的能力包。** skills、MCP、hooks 和任务模板应以 manifest/版本交付，按项目载入，不把所有企业知识和所有工具暴露给每一个 agent。
5. **完成定义必须在实现循环外。** 以 spec/plan/task/验收共同构成 `converge` gate，避免单一 agent 既写实现又自行裁定完成。

## 对个人 AI 工作流的建议

- 对超过一个上下文窗口的任务，维护短 `handoff.md`：当前目标、不可变约束、已验证命令、待决问题、产物路径；不要依赖完整聊天历史恢复工作。
- 建立任务启动的 `effective-policy` 输出：可读/可写目录、允许网络域名、需批准动作、明确 deny 和当前环境变量摘要（不记录 secret 值）。遇到策略不一致时先停止并修正，而不是让 agent 重试。
- 并发前写一行 `subtask contract`：输入、预期文件/证据、最大时长、不能做的动作、汇总者。没有独立验收的任务不要 fan-out。
- 将项目级规范（测试、视觉检查、发布步骤）打包为可版本控制的 skill/plugin；安装时只启用当前仓库所需能力，并在升级后运行 manifest/command 验证。
- 在 PR 前加入 `converge` 清单：逐条对应 spec，确认 diff 没越界，执行独立测试/静态检查，并要求 reviewer 在新提交后重跑受影响项。

## 对项目的含义

本库后续的 CodeGuard/个人 harness 可把 policy manifest 扩为 `effective_policy.json`：静态声明之外记录本次任务实际获准的路径、网络、工具、来源策略和校验时间。再增加一个 `converge` report，将 intent/requirements、变更文件、命令输出、人工批准与 freshness 关联。它先只生成报告和阻止明显越界；积累运行数据后再考虑自动化审批分级。

## 推断与待验证

- **推断**：tool search 与外部化 handoff 的主要收益是减少无关上下文和恢复遗漏，而不保证单次任务更快；可比较 compact 前后 token、恢复耗时和遗漏验收数。
- **待验证**：OpenAI 客户引述的 eval、成本、延迟和失败率改善是否可迁移到个人/小团队，且是否排除了任务分布或环境重构影响。
- **待验证**：集中策略诊断能否显著降低实际越权；需要记录被拦截动作、误拦率、用户绕过尝试和策略漂移，而不是只确认设置页存在。
- **待验证**：Spec Kit 的 converge gate 是否比传统 PR checklist 更能发现需求偏离；可在同类小功能上比较返工率、漏项率与 review 时间。
