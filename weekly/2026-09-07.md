# Weekly Harness Notes - 2026-09-07

## 本周结论

本周的新增材料把问题从“怎样让 agent 多做一些工作”推进到“怎样让高吞吐 agent 不把人和系统拖进新的瓶颈”。共同答案是：把意图、可见上下文、可自动执行的边界与可撤销的验收拆开管理。这样可以允许低风险工作连续运行，同时让高风险动作、敏感上下文和合并决定仍然经过明确的控制面。

### 1. Anthropic《AI-Native SDLC Playbook》：让控制目标随 agent 流动，而不是把旧流程原样加速

来源：[The AI-Native SDLC playbook](https://claude.com/blog/the-ai-native-sdlc-playbook)（2026-08-21）；配套课程：[The AI-Native SDLC Playbook](https://academy.claude.com/courses/ai-native-sdlc-playbook)。

- **有价值的点**：资料明确指出，agent 缩短 build 后，瓶颈会迁移到 plan、review/test 与 deploy；因此应重构整条 SDLC，而非只购买一个写代码的 agent。它建议将需求沉淀为版本化、人与机器都可读的 `intent.md`，并在后续阶段用技能、持续 eval、PR 审查与 hooks 承接同一个意图。
- **痛点**：传统按“人写一行、另一人看一行”设计的审批和交接，无法跟上 agent 放大的 diff；结果不是安全队列堆积，就是绕开检查后低质量发布。
- **方法/机制**：计划阶段把目标、理由和约束写入可版本控制的意图文件；设计/构建阶段把标准编码进 `CLAUDE.md` 与按需 skills；测试阶段把持续 eval 接入 CI；部署阶段用 sandbox、范围受限凭据、MCP 暴露的发布/回滚能力和 hooks 作为确定性闸门。每次控制带被突破，应回写成新的 `intent.md`，形成闭环。
- **效果/结果**：这是 Anthropic Applied AI 团队基于内部实践与客户经验的操作手册，而非独立对照实验。它的可验证主张是：将人工瓶颈替换为可运行控制和自动交接，能使审查/部署能力与 agent 产能一起扩展；具体提效幅度**待验证**。

### 2. Anthropic《Claude Code guide for startups》：把“人人能构建”限定在共享事实与可重建边界内

来源：[The Claude Code guide for startups](https://claude.com/blog/claude-code-guide-for-startups)（2026-08-20）。该文基于十余家创业公司的访谈，属于实务案例汇编，数字为受访企业自述。

- **有价值的点**：非工程角色也可以交付第一版，但前提是 agent 能访问正确的事实来源，并且输出能遵守产品与工程边界。文中把 MCP/成熟 CLI 看作接近真实系统的两条入口；把目录级 `CLAUDE.md` 视为持续规则，把 skills 视为按需流程。
- **痛点**：单靠长提示词无法把业务知识、数据位置、设计规范和反复出现的操作迁移给新人或非技术同事；而把所有知识永久塞进上下文又会陈旧、昂贵且干扰当前任务。
- **方法/机制**：维护可共享的 skills 目录和分目录约束；对大量资料分析或互相审查的任务才 fan-out 子 agent；对大改先用 plan mode，在隔离 worktree 中尝试多种重建；把“内部狗粮—收集反馈—再产品化”作为提升 agent 工具的晋升路径。案例中 ClickHouse 将修复 flaky test、补覆盖率的专用 agent 作为持续贡献者，Clay 则自动化 bug triage。
- **效果/结果**：文章列出 ClickHouse “30% more features shipped”、Omni “2–3x engineering productivity”、Clay “100% of bug triage automated”等受访者数据，不能外推为通用基准。可迁移且更可靠的结论是：先把高频、机械、可验收任务产品化，才有条件扩大自治范围。

### 3. Claude Code Auto mode：用动作分类器替代会产生疲劳的逐命令确认

来源：[Auto mode is now the default in Claude Code](https://claude.com/blog/auto-mode-default-in-claude-code)（2026-08-07）。这是此前未收录的、具有明确安全评测和生产案例的新机制说明。

- **有价值的点**：权限体验不应二选一为“每条命令都问人”或“完全绕过”。Auto mode 在每次工具调用前用分类器判定不可逆、破坏性或越出环境范围的动作；多次被拦截时回退人工确认。
- **痛点**：Anthropic 报告称用户手动同意了 97% 的权限提示，显示逐条审批会退化为条件反射；宽泛的 shell allow-rule 又会把真正的风险检查一并绕开。
- **方法/机制**：保持显式权限规则，但对等同任意代码执行的宽泛 allow-rule 不让其跳过分类器；为 hard deny、敏感数据去向、远端仓库可见性和 destructive Git 操作提供额外上下文；外部工具结果先经过 prompt-injection 筛查。连续三次阻断或会话累计二十次阻断后改走手动批准。
- **效果/结果**：厂商的受控测试中，1,053 名付费测试者手动发现危险命令的比例为 13.6%，Auto mode 阻断 89%；其称采用者产出 PR 多约 25%。这些结果不能直接等价于任意模型/插件组合的安全性，尤其文中所比 Codex 版本已过时；但“基于动作语义、环境状态和回退阈值做分层批准”是可自行复现的 harness 设计。

### 4. GitHub Copilot：把“看什么”和“谁能批准”做成两项独立、可配置的策略

来源：[Content exclusions generally available in Copilot app and CLI](https://github.blog/changelog/2026-09-02-content-exclusions-generally-available-in-copilot-app-and-cli/)（2026-09-02）；[Copilot code review can now approve pull requests](https://github.blog/changelog/2026-09-01-copilot-code-review-can-now-approve-pull-requests/)（2026-09-01）。

- **有价值的点**：GitHub 将上下文准入与合并意见分离。content exclusions 约束 app/CLI 不得把指定文件作为 agent 上下文；代码审查则总能给出“是否可批准”的 assessment，但只有管理员显式打开时才会形成满足 required-approvals 的正式批准。
- **痛点**：权限策略若只约束“能否执行”，机密文件仍可能在任务开始前进入模型上下文；反过来，若将 agent 的评论直接算作合并许可，又会让错误、陈旧 review 或不适配的路径策略扩大影响。
- **方法/机制**：内容排除可在 enterprise、organization、repository 层级配置；正式批准默认关闭，可在三个层级启用，并限定允许 agent 批准的文件路径。新 commit 会像人类审批一样使 agent 的旧批准失效，要求重新 review。
- **效果/结果**：两项功能均处于不同的产品可用范围/preview 状态，未提供可靠的生产质量提升数字。它们的工程价值是把 **context policy、analysis、approval、freshness** 拆为可审计对象；个人项目可用 `.gitignore` 类敏感路径清单、只读审查和“变更后必须重跑验证”来复刻其最小版本。

### 5. `SUNRNEHUI/agent-harness` v10：按“跨边界与风险”选择最轻的持久化协议

来源：[Agent Harness README](https://github.com/SUNRNEHUI/agent-harness/blob/main/README.md)，其 v10.0.0 于 2026-08-27 发布。此项目不以趋势热度入选，而是因本周出现了可检查的重大版本与协议重命名。

- **有价值的点**：仓库反对在模型原生 plan/task 系统之外再造一套永久 prompt 状态机；它只在会话/模型边界或高风险任务需要时外化状态。这和本库以往“所有任务都要日志/记忆”的朴素做法形成有益张力。
- **痛点**：每个小任务都生成 contract、事件日志和审计包会消耗注意力与上下文；完全不留状态又无法跨会话、外部等待或高风险发布恢复、交接和举证。
- **方法/机制**：v10 将项目更名为 Agent Harness，并在显式“write a harness”请求中先生成 intent-to-contract 对齐包与 readiness gate。README 定义三档：Native 使用运行时 Plan 不落额外状态；Portable 使用 `contract.json`、`events.jsonl`、`capsule.md` 穿越边界；Audited 在 Portable 之上增加有理由的证据与审查控制。它同时公开 schema、打包校验与安装包验证脚本。
- **效果/结果**：这是一份开源实现的自我描述，尚无独立基准来证明三档比固定重协议更好，故“节省 token/提升可靠性”是**待验证**。可立即采用的原则是按失败成本和交接需求决定记录粒度，而不是按 agent 是否“看起来复杂”决定。

## 跨来源实践模式

1. **意图是控制面的入口，不是一次性提示词。** 将目标、不可变约束、`done_when` 和证据要求版本化，后续 plan、review、CI 和回滚都引用它。
2. **四个策略面彼此独立。** 最少区分：能看什么（context）、能做什么（capability/action）、何时需要人（approval）、何时结论过期（freshness）。不要以一个“大权限开关”代替它们。
3. **把人工注意力留给例外和判断。** 机械但可验收的工作适合长运行循环；破坏性、跨信任边界或无法自动验收的动作必须转入显式 gate。
4. **状态采用按需持久化。** 当前会话内的低风险任务沿用原生计划；跨会话、跨人或跨系统时，再增加短契约和事件证据；发布/安全任务再升级审计。

## 对个人 AI 工作流的建议

- 在每个超过一小时或可能跨会话的任务开头写 8–15 行 `intent.md`：目标、非目标、允许路径、风险边界、验收命令、停止条件。
- 建立 `context-allowlist`：只向 agent 暴露任务必需的目录；把 `.env`、密钥、客户导出、私有设计稿和无关目录明确排除。**推断**：这会降低上下文泄漏与提示注入面，但仍需结合实际工具的读取方式测试。
- 将权限从“永远允许 shell”改成三档：可逆本地读写自动执行；有副作用但可回滚的动作要求计划/检查点；外发、删除、生产和凭据动作必须人工批准。每次被阻断三次以上，就让 agent 写出替代方案而不是反复重试。
- PR 或交付前执行两套独立门：确定性检查（format、test、diff、secret scan）和语义审查（spec/边界/回归）。任何新提交都应使旧审查和关键验证失效。
- 不要为一次性小修创建庞大“记忆”。只有任务需要移交、等待外部事件或涉及高风险时，才持久化 contract、事件和证据。

## 对项目的含义

本库后续的 CodeGuard/个人 harness 设计可优先实现一个极小的 policy manifest：`context_excludes`、`action_tiers`、`approval_paths`、`freshness_rules` 与每项验收证据。它应先生成 dry-run 报告，再逐步接入 hook/CI，而不是一开始授权 agent 自动部署。

## 推断与待验证

- **推断**：在个人工作流中，context exclusion 的收益通常先体现在减少误导和泄漏风险，而不一定马上表现为速度提升；需要记录 token、返工和拒绝次数来验证。
- **待验证**：Auto mode 的厂商安全结果是否能迁移到本地插件、MCP 服务器、不同 OS 与不同权限模型；不可把其百分比当作通用安全保证。
- **待验证**：`agent-harness` 的 Native/Portable/Audited 三档是否真的降低交接成本。可以随机挑选一组跨会话任务，比较恢复时间、遗漏验收项和证据完整率。
- **待验证**：把 AI review 计入 required approval 是否提高缺陷发现，而不是仅缩短队列；应在限定低风险路径的试点中，追踪撤回率、后续修复率和人类 reviewer 覆盖率。
